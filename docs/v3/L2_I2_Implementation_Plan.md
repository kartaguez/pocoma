I2 transfère la propriété de la transaction physique finale à Engine, extrait Command comme participant métier, livre le fencing final, la suppression R1, le poisoning et l'observation R9. Pas de nouveau module, état durable, reçu de commit, journal de claims, table de compteurs de capacité ou abstraction de locking universelle.

**Raccord I3 :** `ClaimedSlot` est une donnée d'entrée issue d'une acquisition déjà committée ; son contenu n'est jamais une preuve suffisante de validité. I2 revalide la ligne réelle sous verrou. Les tests installent source PENDING et slot/claim par SQL explicite dans une transaction de fixture committée ; ils peuvent remplacer un token sous verrou pour simuler un concurrent. ## 3. Architecture concrète, dépendances et injection

Flux explicite : appel technique déjà claimé → `ConsumptionEngine` → owner physique commun → `ConsumptionSlotStore` et participant `ExecutePotCommand`. Le participant utilise uniquement ses ports métier ; les adaptateurs réalisent SQL/JPA. Engine ignore Pot, Identity, résultat métier, tables métier et familles de séquence métier. La composition choisit une définition, un participant et une autorité ensemble ; incohérence d'autorité refusée avant traitement.

| Propriétaire | Responsabilités exclusives |
|---|---|
| Engine | Ouvrir préparation/finalisation/observation ; état de tentative ; protection finale ; capacité complete liée au slot/token/unité ; vérifier completion/fermeture ; interpréter la résolution physique et décider d'attendre/reprendre. Aucun effet de reprise automatique en I2. |
| Owner physique, adaptateur Spring | Manager/source/EMF exacts ; ConnectionHolder/EntityManagerHolder conservés ; identité physique contrôlée avant **et après** chaque writer ; rollback-only irréversible ; flush ; fermeture/suffixe ; commit/rollback et classification d'incertitude. Il implémente la décision Engine, sans décision métier. |
| Command | Préparer l'intention/faits et proposition jetable ; protéger Identity puis Pot ; appliquer les mutations ; écrire résultat terminal ; appeler complete ; publier métier et observer ses faits durables. Aucun commit/acquisition/cession. |
| Slot adapter | SQL du slot canonique uniquement : verrou final/heure fraîche, validation explicite, DELETE exact, lecture technique pour recovery. Aucun SQL Pot ou découverte caché. |
| Composition | Constructeurs, manager/datasource par autorité, identités et phases actives ; pas de lookup dynamique Spring ni de provider SQL dans le domaine. |

Dépendances futures bornées à déclarer avant modification des POM : `engine-write-pot → engine-consumption` pour implémenter son contrat participant ; `infra-persistence-primary-jpa → infra-tx-spring` (passage de test à compile pour guards) ; `infra-tx-spring` déclare Spring JDBC, Spring ORM et `jakarta.persistence-api` comme dépendances directes de production nécessaires à l'owner ; le starter JPA/PostgreSQL/Flyway/Testcontainers des fixtures L0 reste en scope test. `engine-consumption → port-transaction/domain-consumption` existe déjà ; aucune arête inverse Engine→Pot/infra. Composer via les dépendances existantes de `composition-runtime-spring`. Aucun module ajouté et aucun cycle. Toute impossibilité des règles ArchUnit actuelles exige une règle précisément adaptée avec contre-exemple ; pas d'exception générale « V3 ».

Le port d'owner physique et ses capacités partagées résident dans `port-transaction/.../v3`, consommés réellement par Engine et les writers de publication. Le port de slot, participant, completion et recovery appartient à `engine-consumption/.../v3`, leur consommateur. Le port d'observation métier JDBC reste Command. Aucun Connection/EntityManager/DataSource/TransactionStatus dans ces signatures, les domaines ou les engines.

## 4. Signatures et contrats à réaliser

Contrats Java à fixer tels que ci-dessous, avec les valeurs imbriquées dans leur interface lorsqu'elles n'ont pas d'autre consommateur. Pas de nouveau module pour ces types.

```java
// engine-consumption / com.kartaguez.pocoma.engine.consumption.v3
record ClaimedSlot(ConsumptionId consumptionId, UUID consumableId, UUID claimToken) {}
interface SlotCompletion { void complete(); }
interface ConsumptionParticipant {
    Prepared prepare(UUID consumableId);
    RecoveryObservation observe(UUID consumableId, RecoveryReadContext context);
    interface Prepared {
        void finalizeIn(SlotCompletion completion);
        void requireCompletionReady(); // validation sans mutation, sous l'unité courante
    }
}
enum RecoveryObservation { COMPLETED, NOT_COMPLETED, INCONSISTENT, UNAVAILABLE }
interface RecoveryReadContext { void requireActiveRead(); }
interface ConsumptionSlotStore {
    Protection protectFinal(ClaimedSlot claim); // row lock puis horloge DB séparée
    void deleteProtected(ClaimedSlot claim);   // exactement 1, même unité, pas de test d'heure tardif
    SlotObservation observe(ConsumptionId id, UUID consumableId, RecoveryReadContext context);
}
// Protection = VALID / ABSENT / STALE_OR_EXPIRED ; SlotObservation = valeurs techniques immuables.
// ConsumptionEngine.execute(ClaimedSlot, ConsumptionParticipant) -> Attempt
// Attempt = COMMITTED / CLAIM_LOST / ROLLED_BACK / RECOVERY_PENDING / INCONSISTENT,
// avec cause technique bornée ; jamais PotCommandStore.Result ni résultat fonctionnel READ.

// port-transaction / com.kartaguez.pocoma.port.transaction.v3
interface PhysicalTransactions {
    <T> T snapshot(Supplier<T> action); // RO, REPEATABLE_READ, préparation seulement
    <T> T finalizeUnit(Function<FinalizationUnit, T> action); // RW, READ_COMMITTED
    <T> T observation(Function<ReadUnit, T> action); // RO, REPEATABLE_READ
}
interface FinalizationUnit {
    void requireActive();
    void markSlotProtected(); // Engine seulement, après VALID au verrou final
    void markSlotCompleted(); // Engine seulement, après DELETE réussi
    void requireCompleteAndClosed();
    void poison(Throwable cause);
}
interface ReadUnit { void requireActiveRead(); }
interface PublicationControl {
    void flush();
    void closeAndAppend(Runnable denseSuffix);
}
```

`PhysicalTransactions` ne retourne normalement qu'après résolution confirmée. Sa `Failure` imbriquée porte `ROLLED_BACK` ou `UNKNOWN`, la phase et la cause originale conservée même si le manager la remplace. Un succès physique confirmé est distinct de l'observation métier COMPLETED. `FinalizationUnit` n'est transmis qu'à Engine. `PublicationControl` est la vue étroite injectée au writer Command ; le même adaptateur physique réalise les deux vues, sans nouvel owner.

`RecoveryReadContext` est une vue de `ReadUnit`, liée à l'identité de l'unité, au thread et à sa durée ; ne pas la conserver après callback. Le participant n'appelle pas `PhysicalTransactions` : le contexte ne permet pas de démarrer une transaction. Les ports métier sont injectés par constructeur. Le résultat métier reste dans `PotCommandStore.Result` et dans WRITE ; l'appelant le retrouve par le port Command sous lecture Engine si nécessaire, sans DTO Pot dans Engine.

`ExecutePotCommand.Prepared` reste privé : intention, témoin Identity, workingVersion, résultat, closure d'application typée, références changedComponents ; il implémente Prepared. `prepare` ne traite pas un TERMINAL comme un nouveau succès de finalisation : signal spécifique de faits déjà terminaux → observation R9 par Engine, sans completion ni effets. Toute préparation est abandonnée après échec ; l'Engine ne relance pas au même token. `ClaimedSlot` ne porte pas de deadline copiée ni de ownerToken de partition.

**Détection d'un complete prématuré :** le booléen « appelé » seul est insuffisant. La capacité Engine n'est exposée qu'après protection finale. À chaque appel elle vérifie unité/thread/phase ouverts, unicité, puis appelle `Prepared.requireCompletionReady()` dans la même transaction : source attendue TERMINAL, résultat exact attendu et effets candidate exacts/xid8 (ou aucun effet pour no-op/rejet). Cette vérification de préfixe n'exige pas encore les positions d'événements différées au commit. Elle ne produit aucun effet. Elle échoue avant DELETE si le participant appelle avant résultat/effets. Le participant Command appelle complete exactement après `finishTerminal`. La méthode utilise les faits durables internes, pas un simple drapeau déclaré par le participant. Les gardes de code/DDL et les tests négatifs ferment les voies de contournement ; un participant arbitraire malveillant n'est pas un contrat supporté.

`deleteProtected` n'est accessible qu'au composant Engine ; le participant ne reçoit ni slot store ni clé à substituer. La capacité capture la clé exacte, le token et l'identité d'unité ; mauvais slot/unité/thread, appel réentrant/double, appel après fermeture ou erreur SQL marquent rollback-only même si l'exception est rattrapée. Après completion, les guards de révision/terminalisation/protection métier refusent toute nouvelle mutation ou acquisition de verrou métier ; seul le préfixe de publication explicite peut encore écrire avant fermeture. `PhysicalWriteGuard` distingue dans la même classe `business(source, action)`, `publication(source, action)` et le callback de suffixe : business exige SLOT_PROTECTED, publication exige SLOT_COMPLETED, suffixe exige CLOSED. Le DELETE technique exige SLOT_PROTECTED avant `markSlotCompleted`. Les lectures de validation restent autorisées dans leur phase. Cette distinction empêche une nouvelle mutation Pot après l'appel complete, même avant fermeture. Une capacité conservée après résolution refuse tout accès DB. Si un autre owner Engine est actif, le condamner aussi avant refus.

## 5. Protocole physique R1, dans l'ordre effectif

1. **Entrée déjà claimée.** Le contexte technique a committé un claim ; fixture I2 ou acquisition réelle I3. Vérifier définition/autorité et absence de transaction/synchronization ambiante avant toute préparation. Aucune lecture de partition ownership à la finalisation.
2. **Préparation.** Engine ouvre snapshot WRITE RO REPEATABLE_READ, charge intention/résultat et témoin Identity puis faits Pot sélectifs ; calcule la proposition pure ; clôt ce snapshot. INVALID_BINDING ne consulte ni histoire/version ni verrou Pot. Les faits et la proposition ne sont pas persistés.
3. **Transaction finale.** Engine ouvre une nouvelle unité READ_COMMITTED avec le manager de l'autorité. Le slot adapter fait `SELECT claim_token,claimed_until,state ... WHERE consumption_id=? AND consumable_id=? FOR UPDATE`, puis une **seconde** instruction `SELECT clock_timestamp()`. Pas de `now()`, de timestamp capturé avant attente ou d'horloge Java pour décider le claim.
4. **Fencing après attente.** Ligne présente, état AVAILABLE, token exact, `claimed_until > dbNow`. Sinon sortie claim perdu, aucune participation métier. Le verrou reste détenu jusqu'à résolution physique. Une expiration ultérieure n'annule pas le droit acquis : ne pas re-tester la date dans DELETE. La perte de partition ne change pas ce droit.
5. **Protections Command.** Recharger la demande (intention immuable égale à la préparation, toujours PENDING), protéger le témoin complet Identity, puis sauf INVALID_BINDING advisory Pot `hashtextextended(...,731)`, ligne `v3_pot_identity FOR UPDATE`, comparaison workingVersion. Une absence Pot est protégée par l'advisory. Collision → exception technique/rollback, jamais rejet OBSOLETE synthétique ni recalcul interne.
6. **Effets et résultat.** Closure typée applique candidate et révisions, CAS/xid8/préconditions F2 intacts. Écrire un résultat et CAS PENDING→TERMINAL, chacun avec comptage exact. Aucun slot dans `finishTerminal`. UNCHANGED/REJECTED ne créent aucune version/événement Pot. Le résultat et les révisions ne sont pas encore visibles extérieurement.
7. **Completion R1.** Command appelle `completion.complete()` ; vérification du préfixe décrit au §4 ; DELETE du seul `(C,id,token)` protégé, rowcount=1 ; Engine mémorise completion réussie. Toute faute condamne l'unité. Le slot n'est pas supprimé après suffixe.
8. **Publication métier préfixe.** Command valide l'égalité de changedComponents sur les huit tables à candidate/xid8, stage POT_EVENT et composantes si Changed, puis une COMMAND_COMPLETION_EVENT. Ces INSERT métier précèdent la fermeture. `flush()` JPA ; validation des 18 FK + quatre contraintes B statiques de L1-F, sans ALL IMMEDIATE ; les trois contraintes terminales de publication restent différées. Les INSERT/FK de ce préfixe peuvent encore attendre et doivent être mesurés.
9. **Fermeture puis suffixe.** `closeAndAppend` exige completion réussie et unité saine, ferme irréversiblement les writers métier, exécute le callback SQL suffixe unique : compteur POT s'il existe un événement Pot, sa position, puis compteur COMMAND_COMPLETION et sa position. Seules ces tables/colonnes sont permises dans ce callback, inventaire statique et test de writer post-fermeture. Aucun flush JPA pouvant encore produire du métier après fermeture : le flush précédent doit avoir vidé les intentions d'écriture.
10. **Résolution physique Engine.** Après retour du participant, vérifier un seul complete et publication fermée/suffixe terminé, ressources inchangées et aucun rollback-only. Commit par l'owner, y compris contraintes terminales différées ; conserver les verrous jusque-là. Toute erreur technique ou de protocole → rollback intégral. Observer la résolution réelle ; exception réseau au COMMIT → UNKNOWN si le résultat serveur n'est pas certain, même si callback Hibernate annonce rollback.

État interne en mémoire seulement : unité ouverte sans slot → slot protégé → completion réussie → publication fermée/suffixe terminé → résolue ; POISONED est irréversible et domine toutes phases. Ce n'est pas un nouvel état métier/SQL. Le participant doit retourner après son suffixe. Son retour sans complete ou sans fermeture est un échec, y compris quand aucune mutation Pot n'était nécessaire.

Le writer d'effets doit vérifier les ressources **avant** la première instruction de toute transaction indépendante injectée : détecter REQUIRES_NEW après son commit serait trop tard. Les guards communs mémorisent l'unité extérieure, détectent changement des holders, condamnent celle-ci et refusent l'écriture intérieure. Tester séparément writer d'effets et suppression. Refuser aussi NESTED/savepoint/transaction ambiante, mauvais manager/source et mauvais EMF. Pas de reprise de l'unité après exception interceptée.

## 8. Recovery R9 et décisions de l'Engine

Séparer deux axes : **résolution physique** (COMMITTED, ROLLED_BACK certain, UNKNOWN) et **observation** (les quatre issues R9). Aucun statut UNKNOWN durable. Aucun résultat de callback applicatif ne prouve le commit. L'owner garde phase/causes/synchronization et reconnaît les SQLSTATE transport dans toute chaîne cause/suppressed/nextException ; une erreur pendant COMMIT avec SQLSTATE 08* ou 40003 peut suivre un commit serveur et domine le callback « rolled back ». Rollback non confirmé reste UNKNOWN. Tester aussi manager remplaçant la cause initiale, pas uniquement SQLException directe.

Engine ouvre l'observation RR RO ; lit le slot par son port, puis demande au participant d'observer Command dans **ce même contexte**. `JdbcPotCommandObservation` est un adaptateur du port Command de lecture seule, distinct de `load` qui lançait des exceptions mêlant absence métier et cohérence technique. Il lit intention/source/résultat/completion/position/POT_EVENT et composantes attendues, avec le lien candidate/requestId pour CHANGED. Ne pas exiger que la version soit encore courante : d'autres commandes peuvent avoir avancé le Pot. Vérifier les révisions historiques de la version atteinte et leurs références, sans reconstruire la chaîne entière ni réutiliser le mapper testé pour calculer l'oracle.

NOT_COMPLETED après UNKNOWN ne les autorise pas. COMPLETED résout l'incertitude de la demande ; INCONSISTENT/UNAVAILABLE laissent la reprise bloquée sans effet. La disparition de processus/crash ne fabrique aucun incrément. Aucun `REQUIRES_NEW` dans observe, aucun accès autonome à une seconde base, aucun reçu SQL.
