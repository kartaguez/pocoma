## 3. Scénario réel, transactions et temps

Le test ciblé est **séquentiel**, sans worker concurrent en cours ni attente de 30 secondes ([T], 106–117). Le worker de polling est désactivé ([T], 51–52) ; `orchestrator.run` est appelé directement. Le test concurrent est une autre méthode ([T], 119–130).

| Étape | Appels et effets | Transaction / arbitrage |
|---|---|---|
| Seed | Trois inserts commande, outcome, événement terminal ; instants JVM `Instant.now()` | Pas de transaction de test englobante déclarée ; appels JdbcTemplate séparés ([T], 147–163) |
| Acquisition C1 | `claim` → acquire → service → lifecycle | Transaction A1 via [TXA]/[TX] ; insert slot idempotent, `FOR UPDATE` par clé, insert C1 et installation atomique ([LIFE], 73–120) |
| Expiration artificielle | `UPDATE consumption_claims SET lease_until=now()` | Appel JdbcTemplate séparé, temps PostgreSQL ; ni invalidation ni changement du claim courant ([T], 109–110) |
| Découverte C2 | orchestrator → locator → source.next | Lecture SQL utilisant l'instant JVM capturé à l'ouverture de la recherche ; lease et `next_claim_at` doivent être `<= now` ([LOC], 38–44 ; [SRC], 42–50) |
| Acquisition/takeover C2 | Même acquire, avec un nouvel instant JVM | Transaction A2 ; même slot verrouillé, vérification lease, invalidation C1 `TAKEN_OVER`, création tentative 2, installation C2 ; commit de l'ensemble ([LIFE], 84–120 ; [CLAIM], 18–26) |
| Publication C2 | reload source → materialize → ensureResult | Transaction E2 via [TXE]/[TX] ; insert résultat `ON CONFLICT DO NOTHING` puis comparaison exacte ([MAT], 19–36 ; [STORE], 23–36) |
| Finalisation C2 | provenance puis CAS slot | Toujours E2 ; ajout input, terminalisation seulement si `PENDING` et `current_claim_id=C2`, puis clôture C2 `SUCCESS` ; commit atomique ([EXEC], 47–62 ; [SLOT], 79–92 ; [LIFE], 154–164) |
| Exécution tardive C1 | Même résultat déjà présent, même input que C2 | Transaction E1 ; conflit de provenance attendu avant le CAS (voir §5). Le test exige `DataIntegrityViolationException`, puis un résultat unique ([T], 114–116) |

La configuration instancie un `TransactionTemplate` à partir du `PlatformTransactionManager` et enveloppe acquire/execute/failure ([CFG], 39–44). Aucun niveau d'isolation ni propagation personnalisé n'est fixé par ce code : les valeurs par défaut du gestionnaire s'appliquent. Dans le contexte Spring Boot/JPA mono-datasource du test, JDBC et JPA sont destinés à participer à la même transaction. Cette participation n'a pas pu être confirmée dynamiquement ici ; elle est précisément visée par les tests de rollback [T], 86–103 et [LTEST], 293–316. Il ne faut pas extrapoler à une autre datasource ou un autre gestionnaire.

**Sources temporelles.** Le bean nommé `commandResultClock` est `Clock.systemUTC()` ([CFG], 38), utilisé par acquisition, exécution, failure et locator. L'acquisition échantillonne son instant **avant** l'attente éventuelle du verrou SQL ([ACQ], 28 ; [LIFE], 84). Le locator conserve un instant par recherche, et ne rafraîchit pas le candidat refusé dans cette recherche ([LOC], 40–45). Le test mélange ces instants avec `Instant.now()` pour le seed et `now()` PostgreSQL pour la lease. PostgreSQL exprime ces colonnes en `timestamptz` ([DDL4], 45–48). Aucune mesure de décalage d'horloges, de précision effective ou de latence n'a été obtenue.

**Sémantique essentielle.** L'expiration rend une reprise possible ; elle ne retire pas seule l'autorité de C1. C1 reste autorisé tant que le slot le référence. Le CAS final ne vérifie pas la lease ([SLOT], 85), et [LTEST], 167–178, spécifie explicitement `expiredLeaseKeepsAuthorityUntilTakeover`. Changer ce contrat serait hors mission.

**Verrous et interleavings.** L'acquisition sérialise les repreneurs sur le slot ; le CAS terminal et le retry prennent aussi un verrou d'écriture sur cette ligne ([SLOT], 42, 81–98). Si le takeover committe d'abord, le CAS C1 ne peut plus affecter la ligne et son exécution doit rollbacker. Si la terminalisation C1 obtient le verrou et committe d'abord, l'acquisition observe DONE et ne reprend pas. Les contraintes uniques arbitrent aussi les résultats et provenance. Des attentes de verrous ou un deadlock SQL restent des issues techniques possibles, sans démontrer une publication divergente ; aucun n'a été observé dans cet audit.

La finalisation générique avec effet durable utilise un autre chemin : [FinalizeConsumptionService.java](../../../app/engine-consumption/src/main/java/com/kartaguez/pocoma/engine/service/consumption/FinalizeConsumptionService.java), 27–45, verrouille le claim courant **avant** l'effet. La publication CommandResult réussie passe ici par `ExecuteConsumptionService`, avec fence final après travail métier. Ne pas confondre ces deux chemins.

## 5. Analyse des causes possibles

### Hypothèse test : frontières temporelles

La découverte et le takeover acceptent l'égalité `lease_until <= instant JVM` ([SRC], 44 ; [CLAIM], 23 ; [LIFE], 105–110). `now()` n'est donc pas intrinsèquement incorrect. En revanche, si PostgreSQL est en avance sur la JVM lors de l'UPDATE, la recherche suivante peut encore voir la lease comme future et ne rien traiter. Comme le résultat de `orchestrator.run` est ignoré ([T], 111), le symptôme serait le compteur de résultats différent de 1 à la ligne 112. C'est une **hypothèse conditionnelle**, sans mesure ni trace historique la confirmant.

À l'inverse, si le `now()` SQL est inférieur ou égal au `claimed_at` enregistré par la JVM, l'UPDATE peut lui-même violer `ck_consumption_claims_lease` : la contrainte exige strictement `lease_until > claimed_at` ([DDL4], 58). Décalage d'horloge et précision des timestamps sont donc à distinguer d'un défaut de takeover. Le test bas niveau couvre déjà un cas d'arrondi à la création ([LTEST], 142–152), mais cela ne prouve pas la cause de cet incident.

### Hypothèse test : exception SQL masquant la preuve métier

C2 écrit l'input `(slot, COMMAND_TERMINAL_EVENT, eventId, 1)` ([LOC], 49–50), puis C1 tente d'ajouter exactement le même input ([T], 141–143). `appendInputs` génère un nouvel UUID mais pas une nouvelle identité logique ([PROV], 34–41). L'unicité logique est imposée par `uk_consumption_inputs_identity` ([DDL4], 98). Le flush automatique de la requête terminale peut ainsi lever une violation d'unicité **avant** que son prédicat de fencing soit évalué ([SLOT], 79 ; [EXEC], 47–61).

Le résultat lui-même est rejoué de manière idempotente par `ON CONFLICT DO NOTHING`, pas par une violation d'unicité sur `command_results` ([STORE], 26–35). La contrainte de provenance est donc l'explication statique attendue du `DataIntegrityViolationException`. Sans stacktrace/SQLSTATE observé, son origine exacte reste non confirmée dynamiquement.

Conséquence certaine : ce scénario pourrait encore passer si le CAS de fencing était incorrect, puisque la provenance arrêterait C1 avant lui. Il prouve une absence de duplication dans ce chemin, mais ne constitue pas isolément une preuve directe du fence. Une sensibilité au moment du flush ou à la traduction d'exception est plausible ; aucune variation observée ne la démontre comme source de flakiness.

### Hypothèse runtime

Le code inspecté lie les effets SQL et le CAS dans une transaction, sérialise les acquisitions et conserve l'unicité des résultats ([TXE], [EXEC], [LIFE], [STORE], [DDL25]). Aucun chemin établi ne permet à C1 de committer un effet autoritaire après remplacement de son claim. Cependant, le scénario ciblé ne maintient pas une transaction C1 ouverte pendant le takeover, et le test voisin lance deux workers sans imposer leurs interleavings ([T], 119–129). L'absence de défaut trouvé statiquement ne vaut pas preuve de toutes les courses.

### Hypothèse environnement

Le blocage Docker/cache est établi **pour cette session**. PostgreSQL/Testcontainers, charge, ordonnancement, horloges hôte/VM et ressources CI restent des facteurs historiques possibles, sans corrélation disponible. Les timeouts de 10 secondes appartiennent au test voisin ([T], 124–125), pas au scénario ciblé. L'image PostgreSQL est référencée par tag ([T], 54) : comparer les digests serait utile lors d'une reproduction, sans changer le test durant l'audit.

### Diagnostic retenu

**INCONCLUSIVE**, et non `TEST_FLAKINESS`, `RUNTIME_DEFECT` ou `ENVIRONMENTAL` pour l'incident historique : aucune reproduction ni trace initiale détaillée ne permet d'attribuer la cause. Le test comporte des faiblesses de déterminisme et de pouvoir discriminant démontrables par lecture. Elles justifient une proposition de fiabilisation, pas un diagnostic causal définitif ni une correction runtime.

## 7. Proposition minimale, sans application

Fichier principal : [T]. Aucun changement runtime ou SQL de production proposé. Une éventuelle mise à jour de [Debt.md](Debt.md) ne devra intervenir qu'après validation du diagnostic et des preuves.

1. **Préférer une horloge contrôlée dans le contexte du test.** Remplacer uniquement le bean de test nommé `commandResultClock` (les injections sont qualifiées, [CFG], 42–46), acquérir à un instant `t0` représentable à la microseconde, puis avancer explicitement à `t0 + 31 s` avant la découverte/takeover. Utiliser la même horloge pour acquire, locator, execute et failure. Réinitialiser l'horloge entre méthodes. Cela conserve la lease réelle stockée et supprime l'UPDATE temporel artificiel. Le seed peut utiliser ce même instant pour la cohérence de fixture.
2. **Si une expiration SQL est préférée**, positionner la lease strictement avant l'instant utilisé par le consommateur et maintenir `claimed_at < lease_until`, ainsi que toutes les contraintes de lifecycle. Un simple `lease_until=now()-interval '1 minute'` sur le claim fraîchement créé serait invalide. Déplacer aussi `claimed_at` et les dates cohérentes de fixture exige plus de précautions ; ne pas le faire sans assertion sur les lignes affectées et les contraintes. L'horloge contrôlée est plus lisible ici.
3. **Observer le takeover.** Capturer le retour de `orchestrator.run`, vérifier absence de `RuntimeFailure` et nombre d'exécutions, puis lire les deux claims du slot : C1 `TAKEN_OVER` avec `invalidated_at`, C2 distinct, worker `takeover`, tentative 2, fin `SUCCESS`. Vérifier slot DONE/SUCCESS sans claim courant et une seule provenance attendue. Pour une preuve avant finalisation, acquérir C2 explicitement et vérifier `AcquireResult.Acquired`/`current_claim_id=C2`, tout en conservant un scénario passant par locator/orchestrator.
4. **Séparer la preuve du fence et la preuve du rejeu.** Conserver le rejeu tardif avec la provenance réelle si utile, mais ne pas considérer son `DataIntegrityViolationException` comme contrat de fencing. Ajouter un chemin de test C1 qui tente un effet SQL durable observable sans provoquer de doublon de provenance (par exemple une provenance distincte de test), atteint le CAS, exige `LostClaimException` et vérifie rollback de cet effet/provenance. Ne pas simplement remplacer l'assertion actuelle par `LostClaimException` : le conflit existant peut empêcher d'y arriver. Ne pas élargir à `RuntimeException` ni supprimer les assertions persistantes.
5. **Comparer les états complets avant/après stale**, y compris contenu/propriétaire/version du résultat et états des deux claims, pas seulement `count(*)`. Préserver les tests rollback et deux workers. Pour prouver la course réelle, ajouter ultérieurement une coordination par barrières : C1 engagé avant takeover, C2 reprend/commit, C1 reprend et rollbacke. Les timeouts servent seulement à borner un blocage, jamais à provoquer l'expiration. Aucun sleep ou retry masquant un échec.

Un helper interne à [T] suffit potentiellement pour l'horloge ; pas besoin de modifier `CommandResultRuntimeConfiguration` en production. Cette proposition améliore la preuve mais ne doit pas effacer la baseline avant qu'une reproduction sur environnement valide ait été tentée.
