# Functional Model — CURRENT

État livré au HEAD `c14751f` (2026-10-03). Ce texte décrit les comportements observables. Les mécanismes et leurs limites de preuve figurent dans [Architecture](../architecture/Architecture.md) et [System Guarantees](../guarantees/System_Guarantees.md). Une admission acceptée, une décision métier terminale et une vue de lecture disponible sont trois moments distincts.

## Identité et inscription

Une **ExternalIdentity** est le couple `(issuer, subject)` attesté par l'authentification. Un **User** est l'identité interne. Un **Binding** rattache une ExternalIdentity à un User pendant une occurrence de vie identifiée par un **BindingId** ; une nouvelle occurrence n'est pas l'ancienne même si elle concerne le même couple. L'état courant peut être `ATTACHED` ou `DETACHED`. Un Command capture le BindingId présenté à l'admission et l'exécution vérifie que cette occurrence est encore courante. L'admission ne prouve donc pas l'autorisation métier future.

`POST /api/v1/registrations` accepte un corps vide ou `{}` et retourne `202` avec `requestId`. Le **RegistrationRequest** durable porte l'ExternalIdentity du demandeur. Son traitement arbitre l'acquisition du Binding et la création du User : `REGISTERED` rend `userId` et `bindingId`, `REJECTED` rend le code `EXTERNAL_IDENTITY_ALREADY_USED`. Une décision déjà enregistrée est réutilisée. `GET /api/v1/registrations/{requestId}/result` rend `200` avec la décision matérialisée, ou `404` si elle n'est pas encore disponible, est absente, ou n'appartient pas à l'ExternalIdentity authentifiée. La visibilité du Result est attachée au demandeur historique, même si son Binding courant change ensuite. `REGISTERED` ne dépend pas de la disponibilité de CURRENT_BINDING.

Après `REGISTERED`, la vue `GET /api/v1/me/binding` peut encore rendre `404` : la publication du Binding courant est indépendante et asynchrone. Lorsqu'elle rend `200`, elle fournit l'occurrence courante nécessaire au premier Command. Le client soumet ensuite ce `bindingId` avec `commandType` et `payload` à `POST /api/v1/commands`. Un Binding détaché est une tombstone de la vue courante, pas un nouveau User implicite.

## Commands et Results

`POST /api/v1/commands` retourne `202` et `commandId` après admission durable. Le résultat métier vient plus tard : `GET /api/v1/commands/{commandId}/result` (également `/api/v1/command-results/{commandId}`) rend `APPLIED` avec `potId` et `resultingVersion`, `REJECTED` avec un code métier, ou `FAILED` avec un code public ; sinon `404`. Le `404` couvre aussi un autre propriétaire. Le Result reste visible par l'ExternalIdentity qui a soumis le Command, indépendamment de son Binding courant. Un `202` ne promet ni `APPLIED`, ni une projection Pot déjà prête.

Les Commands livrés portent sur la création, la modification et la suppression de Pot ou d'Expense, ainsi que les membres et parts du Pot. Un **Pot** est l'objet métier versionné ; ses membres et leurs parts/poids sont modifiés par ces Commands. L'ownership et les relations d'un Pot participent à l'autorisation d'une lecture. Les droits observables combinent les capacités du jeton (dont `POT_VIEW`) et les relations du demandeur avec le Pot à la version demandée. Une capacité seule ne confère pas accès à un Pot quelconque. Le contrat cible plus large d'[authorization-kernel-contracts](../architecture/authorization-kernel-contracts.md) est **TARGET** ; seule la route exacte ci-dessous est décrite ici.

## Lecture exacte du Pot

`GET /api/v1/pots/{potId}?version=V`, lorsqu'activé, demande `V >= 1` explicitement. La lecture utilise l'autorisation `AUTH@V` puis le contenu `READ_POT@V`. Elle retourne `200` pour cette version exacte si les deux vues sont prêtes et l'accès permis. Elle rend `404` opaque si l'identité interne n'est pas résolue ou si l'accès est refusé ; `409 POT_NOT_READY` si une vue nécessaire n'est pas encore prête ; `503 POT_PROJECTION_FAILED` si une projection nécessaire a échoué. `400 INVALID_VERSION` couvre `V < 1`. Cette route ne choisit pas automatiquement une version « current », « head », « latest known » ou « serving ». L’ExternalIdentity doit être résolue vers un User avant que la lecture autorisée soit possible.

Les contrôleurs d'admission valident aussi les enveloppes et peuvent rendre `400` ; le principal invalide peut rendre `401`, un media type non accepté `415`. Les routes Command et Pot sont soumises à leurs propriétés d'activation. Aucun listing Pot ou endpoint CURRENT Pot n'est déclaré ici comme contrat livré.
