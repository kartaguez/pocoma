# Matérialisations READ — audit d'écart et plan global

Statut : **cible architecturale et plan, sans implémentation**. Branche : `v2-make-it-pull`, inspection au commit `2a43987b15e002db15b1bfdb0782563002c82588` (2026-10-03). La [baseline descriptive](Read_Usage_and_Derived_Materialization_Audit.md) décrit les usages livrés ; le présent document fixe la cible et prévaut sur les directions incompatibles du [plan Registration](../REGISTRATION/Step_Plan.md) et de l'[audit Registration antérieur](../REGISTRATION/Current_Binding_Registration_Architecture_Audit.md). Les chemins `app/` ci-dessous désignent des fichiers réels du checkout inspecté. Aucun code ni schéma n'a été changé par cet audit.

## 1. Contrats canoniques et baseline

`E = ExternalIdentity(issuer, subject)` attestée par l'AuthN ; le `subject` doit être durable et non réattribuable dans son issuer. Email et autres attributs mutables ne sont pas des substituts. `U = PocomaUserId`. `B = BindingId`, occurrence durable et historiquement significative d'association E/U, non secrète et non credential. Pour **toute nouvelle intention au nom de U**, l'enveloppe contient E authentifiée et B. WRITE vérifie autoritativement l'occurrence exacte et courante `B ∈ E`, résout `(E,B) → U`, puis contrôle le métier. Un ancien B1 après detach puis B2 est refusé, jamais réinterprété sous B2. Une intention acceptée conserve immuablement `requesterExternalIdentity=E` ; son résultat historique est consultable par E avec l'intentionId, sans B courant et sans B fourni au GET. Un autre E reçoit un 404 opaque.

Registration précède tout binding : `RegistrationRequest(requestId,E,payload)` est durable avant que le POST rende son identifiant ; aucun B à l'admission. Le terminal `Registered(U,B)` ou `Rejected(EXTERNAL_IDENTITY_ALREADY_USED)` est unique. Un succès crée atomiquement U, le binding autoritatif E/B/U, l'outcome et les faits métier ; un rejet ne crée aucun B. `REGISTRATION_RESULT` dérive de l'outcome terminal, `CURRENT_BINDING` du fait Binding. Les deux convergent indépendamment ; aucun READ ne dépend d'un autre READ. Le GET Registration Result autorise E enregistrée sur la request, même après detach ou remplacement. Aucun ResponseToken n'est requis par les faits connus.

| Contrat | Question et clé | Écriture cible | Source actuelle |
|---|---|---|---|
| Versioned Projection | représentation de `(type,objectId,V)` | artifact immutable pour chaque V ; `ensureExact` | Business Event → ProjectionTask → projector → root/artifact |
| Result | terminal de `intentionId` | zéro puis un résultat immutable, idempotent, owner E ; aucune version métier | COMMAND_RESULT : terminal Event → Task → root/artifact `V=1` ; Registration absent |
| Current Materialization | valeur valide maintenant pour E | `advance(E,R,value)` uniquement si `R > stored.R` ; tombstone | Binding Fact → Consumption → upsert current |

Cette distinction est dans le **contrat d'écriture**, pas dans l'existence de workers séparés. La source de chaque dérivation est un fait autoritatif durable consommable. Un terminal Event Command et un Binding Fact suffisent déjà ; créer un Event de pure conversion ou une ResultTask durable demande une propriété supplémentaire démontrée.

## 3. Pipelines actuels et cibles

### Versioned Projection

Actuel et cible : `business_event_outbox` → `JdbcProjectionMaterializationDiscoveryAdapter` → Consumption Event → `ProjectionMaterializationConsumptionService` → `ProjectionTask × N` → Consumption Task → loader/projector/validator → `projection_root` + `projection_artifact`. Les roots sont uniques par `(type,objectType,objectId,V)` (READ V7). `AUTH@V`, `READ_POT@V`, `POT_BALANCES@V` restent ici. Le fan-out et les retries indépendants donnent une raison concrète de garder Task. Tests : `runtime-event-consumption-worker/.../ProjectionMaterializationConsumptionPostgresTest.java`, `runtime-task-consumption-worker/.../CanonicalProjectionTaskRuntimePostgresTest.java`, `infra-read-persistence/.../JdbcProjectionStoreAdapterPostgresTest.java`.

### COMMAND_RESULT — trace complète

1. `ExecuteRecordedCommandService` produit `CommandOutcome.Applied/Rejected/Failed`. `JdbcCommandOutcomeAdapter` écrit `command_outcomes` et `command_terminal_events` dans le commit fenced Command ; WRITE V17 impose outcome unique et terminal Event unique par commandId. `Failed` est ici **un outcome terminal autoritatif public** (`COMMAND_PROCESSING_FAILED`), à distinguer d'une failure de projection.
2. `JdbcProjectionMaterializationDiscoveryAdapter` découvre aussi les terminal Events ; `PocomaProjectionMaterializationPolicy` route APPLIED/REJECTED/FAILED vers `COMMAND_RESULT`. `ProjectionMaterializationConsumptionService` assure une Task `(COMMAND_RESULT,COMMAND,commandId,1)` sous le slot Event.
3. `runtime-task-consumption-worker/.../CanonicalProjectionTaskRuntimeConfiguration.java` catalogue le producer ; `JdbcCommandResultProjectionInputLoader` recharge outcome et E capturée sous `REPEATABLE_READ`. `CommandResultProjector` construit le JSON ; `CommandResultProjectionDefinition` et le validator le contrôlent. `ProjectionTaskConsumptionService` publie root/artifact via `JdbcProjectionStoreAdapter` sous finalisation fenced, ou enregistre `projection_failure` sur terminal technique ; retry temporaire via `HandleConsumptionFailureUseCase`.
4. `GetCommandResultService` lit l'artifact exact V1, vérifie cohérence et E, masque absent/non-prêt/failure/non-owner par `NotFound` ; `CommandResultController` donne 404. READ V14 interdit un ancien artifact sans E exacte. La lecture ne demande déjà pas B courant.

Cible minimale : conserver outcome, terminal Event, E enregistrée, GET et sa sémantique ; consommer **directement** `command_terminal_events` avec les primitives Consumption existantes ; recharger outcome + E ; `ensureResult(commandId,E,terminalOutcome)` dans un store Result immutable, dans la même transaction que la finalisation fenced du slot. Le terminal Event est déjà durable et unique : aucune ResultTask par défaut. Il faut un consumer identity distinct de l'ancien Event→Task pour permettre le cutover/replay sans collision de slots. Le chargement peut se faire avant la transaction finale, mais l'égalité id/outcome/E et le commit du Result doivent être protégés par le fence ; valider aussi l'état terminal relu. Une réexécution avec contenu identique est no-op ; contenu divergent à même id est une erreur, pas « first root wins ». Après preuve de parité et drain/backfill, retirer seulement la route Command, le loader/projector/definition et les tasks historiques devenus inutiles. Ne pas toucher aux Tasks Pot.

Les preuves CCR à **adapter, non supprimer** : `architecture-tests/.../ccr/CommandResultProjectionChainPostgresTest.java` doit devenir terminal Event→Result, en gardant les assertions de terminalité, E, concurrence, retry et séparation des commits ; `CommandCompletionE2EPostgresTest.java` doit lire le nouveau store, garder APPLIED/REJECTED/FAILED, 404 cross-E et ancien résultat après changement de B ; `infra-read-persistence/.../CommandResultExactIdentityCutoverMigrationPostgresTest.java` doit devenir preuve de migration/parité des anciens artifacts. `runtime-event-consumption-worker/.../PocomaProjectionMaterializationPolicyTest.java` et `ProjectionMaterializationConsumptionPostgresTest.java` retirent seulement la route Command après bascule. `runtime-task-consumption-worker/.../CanonicalProjectionTaskRuntimePostgresTest.java` garde les preuves Pot@V. Les tests de `GetCommandResultService`, du contrôleur et de fence Command restent pertinents.

### REGISTRATION_RESULT

Absent aujourd'hui. Cible : POST AuthN E → request immutable et durable → 202 avec requestId → Consumption Registration → transition terminale atomique (outcome +, sur succès, U/binding/faits) → source terminale durable → Consumption Result → recharge request/outcome → `ensureResult(requestId,E,Registered(U,B)|Rejected(code))` → GET `requestId + authenticated E`. Pas de version 1, Task, root/artifact, ResponseToken ou lecture de CURRENT_BINDING au GET. Le terminal outcome peut servir directement si discovery fiable, ordonnée et rejouable ; un terminal Event est acceptable seulement s'il apporte un contrat durable clair de découverte/provenance ou de fan-out, atomique avec l'outcome. Le succès alimente **indépendamment** `external_identity_binding_facts` → worker Binding → CURRENT_BINDING. Le rejet n'émet aucun fait Binding et son Result reste lisible.

### CURRENT_BINDING

Actuel et cible : `JpaExternalIdentityBindingAdapter` modifie l'autorité et append le fait sous la même transaction ; `JdbcBindingFactDiscoveryAdapter`/`BindingFactConsumptionLocator` découvrent et rechargent le fait par `event_id` ; Consumption Binding protège le commit ; `JdbcCurrentBindingAdapter.apply` fait `ON CONFLICT (issuer,subject) ... WHERE excluded.binding_revision > current.binding_revision`. À R égal, payload identique = duplicate ; divergent = invariant violation. R inférieur = stale. `DETACHED` conserve la ligne et R, avec U/B nuls (READ V11/V12) ; absence fonctionnelle au GET et présence physique de convergence sont distinctes. R0 migré est légitime, sans problème de `ProjectionKey >= 1`. Conserver le runtime direct et les tests `BindingRuntimePostgresTest`, `CurrentBindingPersistencePostgresTest`, `CurrentBindingTerminalCutoverMigrationPostgresTest` ; compléter uniquement les cas manquants. La règle est `none+R1 apply`, `R1+R2 apply`, `R2+R2/no-op`, `R2+R1/no-op`, `R2+R5 apply`, `R5+R4/no-op`.

## 4. Consumption, stockage et failures

`domain-consumption` définit clés, slots, claims, lease, états et provenance. `engine-consumption` fournit `AcquireConsumptionService`, `ExecuteConsumptionService`, `FinalizeConsumptionService`, `HandleConsumptionFailureService`, ports lifecycle/provenance, CAS de claim et effet durable fenced ; `orchestrator-consumption` fournit discovery bornée, budgets et `AcquireThenFinalizeConsumptionOrchestrator`/`SequentialConsumptionOrchestrator`. `supra-consumption-worker` assure le polling. Les locators Event, Binding, LKV et Command adaptent **leur source**, leur reload, leur classification et leurs effets ; ils ne réimplémentent pas le protocole. Le plan Result doit composer ces primitives, pas bâtir une deuxième infrastructure de worker. `ProjectionTaskConsumptionOrchestrator` et `ProjectionTaskConsumptionService` restent spécifiques à Task et publication Projection ; leur dépendance à `engine-projection-task` dans `orchestrator-consumption` est un point de placement à corriger si la fondation commune est touchée. Le contrat générique ne connaît pas `ProjectionKey` et ne doit pas l'apprendre.

Stockage : conserver READ V7 `projection_root/artifact` pour les exactes V. Conserver `current_external_identity_binding` et sa révision. Pour Result, comparer au lot infrastructure : (a) table générique à clé `(result_type,intention_id)` avec colonnes owner issuer/subject, type, schema_version et payload JSONB discriminé ; (b) tables dédiées Command/Registration avec colonnes métier et contraintes shape ; (c) root/result générique sans version métier. La table générique évite deux stores presque identiques et facilite `ensureResult`, mais nécessite contraintes par type, validation JSON et évolution de schéma ; les tables dédiées donnent des CHECK/FK précis mais dupliquent le protocole ; root/result n'est justifié que si des métadonnées communes prouvées l'exigent. Recommandation provisoire : contrat/port commun `ensureResult` + read owner, représentation physique choisie après comparaison SQL de contraintes, requêtes par id, payloads, migrations et coût du cutover. Le versioning de **schéma JSON** est permis, distinct de la version métier de Result. Ne conserver aucun Result dans `projection_artifact` pour éviter une migration. READ V14, les résultats existants, la reprise et une période de double lecture contrôlée doivent être traités explicitement ; éviter deux writers concurrents sur le même résultat.

Failure : `projection_failure` (READ V7 ; `JdbcProjectionStoreAdapter.recordFailure/hasFailure`) est une marque technique indexée par ProjectionKey ; `ExactProjectionReadService` la convertit en `Failed`, puis `GetCommandResultService` en 404. Elle n'est pas un outcome Command. En quittant Task, Result a besoin de retries/claim et d'un diagnostic opérationnel de matérialisation, avec replay/rebuild depuis l'outcome terminal ; un état failure technique peut être conservé par les slots Consumption, éventuellement complété par un registre Result seulement si les opérations de reconstruction ou la visibilité le demandent. Ne copier ni `projection_failure` ni un `FAILED` technique public par réflexe. Un `CommandOutcome.Failed` demeure un résultat métier/protocole terminal public ; une exception du writer Result ne l'est pas. La même séparation vaut pour Registration, dont le canon n'admet que Registered/Rejected. Avant cutover, établir la procédure pour les anciennes `projection_failure` Command, leurs slots et les Events terminaux afin qu'aucun résultat historique ne soit perdu ou figé en 404. Tester retry, poison input, perte de claim, rollback et reconstruction idempotente.

## 7. Décisions humaines résiduelles

1. Forme SQL Result après prototype de contraintes : table générique, tables dédiées ou root/result ; fixer version de schéma JSON, FK, stratégie de lecture des artifacts historiques et durée de compatibilité. Le contrat immutable et l'owner E sont déjà décidés.
2. Source de découverte Registration Result : outcome directement découvrable ou terminal Event atomique si la discovery, la provenance ou le fan-out l'exigent. Aucune ResultTask par défaut.
3. Politique opérationnelle des failures permanentes de matérialisation Result : slot Consumption seul ou registre Result additionnel, procédure de réparation et métriques. Aucune failure technique ne devient un outcome public.
4. Moment et méthode de cutover des anciens COMMAND_RESULT, de leurs `projection_failure` et tasks : backfill/parité, lecture transitoire et retrait après drain. La conservation des anciens résultats est obligatoire.
5. Si l'issuer externe ne garantit pas un subject durable non réattribuable, définir une mitigation au niveau AuthN/issuer avant de s'appuyer sur l'ownership E. Aucun ResponseToken n'est introduit par défaut.
