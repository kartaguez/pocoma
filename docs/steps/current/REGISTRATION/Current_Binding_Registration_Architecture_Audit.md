## B. CURRENT_BINDING actuel : format et production

La forme métier READ est [`CurrentBinding`](../../../../app/engine-read-projection/src/main/java/com/kartaguez/pocoma/engine/read/binding/CurrentBinding.java) : identité externe E, révision R, statut ATTACHED/DETACHED, U/B seulement si attaché, `sourceEventId` et horodatage. [`JdbcCurrentBindingAdapter`](../../../../app/infra-read-persistence/src/main/java/com/kartaguez/pocoma/infra/read/persistence/JdbcCurrentBindingAdapter.java) maintient **une ligne mutable par `(issuer,subject)`** dans `pocoma_read.current_external_identity_binding` ([READ V9](../../../../app/infra-read-persistence/src/main/resources/db/read-store/migration/V9__current_external_identity_binding.sql), [V11](../../../../app/infra-read-persistence/src/main/resources/db/read-store/migration/V11__current_binding_canonical_detached.sql), [V12](../../../../app/infra-read-persistence/src/main/resources/db/read-store/migration/V12__current_binding_fact_provenance.sql)). L'upsert n'accepte que R supérieur, classe R inférieur STALE et R identique/payload identique DUPLICATE ; une divergence à R identique est une erreur. [READ V13](../../../../app/infra-read-persistence/src/main/resources/db/read-store/migration/V13__verify_terminal_binding_facts.sql) confronte la vue aux faits terminaux.

**Format :** une projection matérialisée au sens métier, avec provenance et monotonie. **Format standard Pocoma : non.** Aucune `ProjectionKey`, `ProjectionDefinition`, validation JSON, `projection_root`/`projection_artifact` ou version de root n'est utilisée pour ce type. La version visible est R du stream Binding, qui peut valoir 0 pour une baseline migrée ; le root standard exige `targetVersion >= 1` ([`ProjectionKey`](../../../../app/domain-projection/src/main/java/com/kartaguez/pocoma/domain/projection/ProjectionKey.java), [READ V7](../../../../app/infra-read-persistence/src/main/resources/db/read-store/migration/V7__canonical_projection_store.sql)). Le port [`CurrentBindingProjectionPort`](../../../../app/engine-read-projection/src/main/java/com/kartaguez/pocoma/engine/read/binding/CurrentBindingProjectionPort.java) n'est pas `ProjectionWritePort`. Il n'existe ni projector dédié, ni route, ni validation de task CURRENT_BINDING dans le catalogue standard.

**Chaîne réelle :** `JpaExternalIdentityBindingAdapter.acquire/detach` verrouille le stream E, modifie l'autorité, avance R et append un fait `ExternalIdentityAttached/Detached` dans la même transaction ([adapter](../../../../app/infra-persistence-jpa/src/main/java/com/kartaguez/pocoma/infra/persistence/jpa/adapter/identity/JpaExternalIdentityBindingAdapter.java), [WRITE V20](../../../../app/infra-persistence-jpa/src/main/resources/db/migration/V20__external_identity_binding_lifecycle.sql), [V21](../../../../app/infra-persistence-jpa/src/main/resources/db/migration/V21__binding_occurrences_and_fact_expand.sql), [V22](../../../../app/infra-persistence-jpa/src/main/resources/db/migration/V22__repair_binding_history_and_contract.sql), [V23](../../../../app/infra-persistence-jpa/src/main/resources/db/migration/V23__close_binding_fact_type_contract.sql)). Après commit, [`JdbcBindingFactDiscoveryAdapter`](../../../../app/infra-persistence-jpa/src/main/java/com/kartaguez/pocoma/infra/persistence/jpa/adapter/identity/JdbcBindingFactDiscoveryAdapter.java) découvre directement les faits éligibles. [`BindingFactConsumptionLocator`](../../../../app/locator-consumption-binding/src/main/java/com/kartaguez/pocoma/locator/consumption/binding/BindingFactConsumptionLocator.java) recharge le fait par `eventId`, fabrique `CurrentBinding` et appelle `apply`. Le [runtime Binding](../../../../app/runtime-binding-consumption-worker/src/main/java/com/kartaguez/pocoma/runtime/binding/BindingRuntimeConfiguration.java) utilise le protocole générique de claim/lease/CAS pour le consommable `IDENTITY_BINDING_FACT/eventId`, consumer `CURRENT_BINDING_PROJECTOR`. L'apply READ et la finalisation du claim ont lieu dans l'exécution transactionnelle de Consumption. Le champ `event_id` du fait est une provenance durable ; **ce fait n'est actuellement ni découvert comme Event par le worker Event, ni transformé en ProjectionTask**. Aucun producteur ne crée de task CURRENT_BINDING. Le worker Binding est l'unique producteur effectif de la ligne READ.

## C. Pipeline Event → ProjectionTask → projection effectivement livré

[`PocomaProjectionMaterializationPolicy`](../../../../app/runtime-event-consumption-worker/src/main/java/com/kartaguez/pocoma/runtime/event/consumption/PocomaProjectionMaterializationPolicy.java) associe exhaustivement les types Pot à AUTH/READ_POT/POT_BALANCES et les trois events terminaux Command à COMMAND_RESULT ; [`ProjectionMaterializationPolicy`](../../../../app/engine-processing-event/src/main/java/com/kartaguez/pocoma/engine/processing/event/materialization/ProjectionMaterializationPolicy.java) vérifie la couverture des types connus. [`JdbcProjectionMaterializationDiscoveryAdapter`](../../../../app/infra-persistence-jpa/src/main/java/com/kartaguez/pocoma/infra/persistence/jpa/adapter/processing/event/JdbcProjectionMaterializationDiscoveryAdapter.java) fait un `UNION ALL` de `business_event_outbox` et `command_terminal_events`, joint les routes par `event_type`, segmente et écarte les consommations DONE. Il produit les métadonnées `(eventId, projectionType, targetType, targetId, targetVersion, recordedAt)` ; il ne recharge pas le payload. Cette union SQL codée en dur ne couvre aucun fait Binding. Le [runtime Event](../../../../app/runtime-event-consumption-worker/src/main/java/com/kartaguez/pocoma/runtime/event/consumption/EventConsumptionRuntimeConfiguration.java) filtre les types configurés, acquiert un claim `EVENT/eventId + PROJECTION_TASK_MATERIALIZER/projectionType`, puis [`ProjectionMaterializationConsumptionService`](../../../../app/locator-consumption-event/src/main/java/com/kartaguez/pocoma/locator/consumption/event/materialization/ProjectionMaterializationConsumptionService.java) appelle `ProjectionTaskStorePort.ensure` **dans la finalisation fenced**. L'insert `ON CONFLICT DO NOTHING` et l'unicité `(projectionType,targetType,targetId,targetVersion)` dans [WRITE V13](../../../../app/infra-persistence-jpa/src/main/resources/db/migration/V13__canonical_projection_tasks.sql) rendent la planification idempotente. Ce commit est distinct du commit de l'event primaire.

[`JdbcProjectionTaskStoreAdapter`](../../../../app/infra-persistence-jpa/src/main/java/com/kartaguez/pocoma/infra/persistence/jpa/adapter/projection/JdbcProjectionTaskStoreAdapter.java) découvre les tasks par type/segment en excluant les slots DONE. [`ProjectionTaskConsumptionOrchestrator`](../../../../app/orchestrator-consumption/src/main/java/com/kartaguez/pocoma/orchestrator/consumption/ProjectionTaskConsumptionOrchestrator.java) acquiert une clé de task, puis prépare hors transaction d'acquisition. [`ProjectionEngineService`](../../../../app/engine-projection-task/src/main/java/com/kartaguez/pocoma/engine/projection/task/engine/ProjectionEngineService.java) sélectionne la déclaration par type, vérifie le target, charge l'input autoritatif, appelle le projector, vérifie la clé et valide le `ProjectionDefinition`/schéma. Le [runtime Task](../../../../app/runtime-task-consumption-worker/src/main/java/com/kartaguez/pocoma/runtime/task/consumption/CanonicalProjectionTaskRuntimeConfiguration.java) câble catalogue, loader, projector, validation et types effectivement servis. [`ProjectionTaskConsumptionService`](../../../../app/engine-projection-task/src/main/java/com/kartaguez/pocoma/engine/projection/task/ProjectionTaskConsumptionService.java) publie l'artefact ou l'échec terminal dans la finalisation fenced ; l'échec temporaire suit le retry. [`JdbcProjectionStoreAdapter`](../../../../app/infra-projection-persistence/src/main/java/com/kartaguez/pocoma/infra/projection/persistence/JdbcProjectionStoreAdapter.java) publie un root et ses artefacts immutables, idempotents par clé, dans le store READ. Ce second commit est distinct du premier et de l'event.

Les claims/leases/CAS et la contrainte unique protègent du double travail durable sous plusieurs workers ; les retries peuvent recalculer, mais une finalisation perdant son claim ne doit pas publier. **Limite essentielle :** l'unicité d'un root par version empêche les doublons, pas la régression d'une *vue courante* quand R1 finit après R2. Le store standard est immutable par clé ; il ne sait pas, seul, maintenir la ligne mutable `CURRENT_BINDING` ni rejeter une projection ancienne. Les tests de base existants comprennent [`EventConsumptionRuntimePostgresTest`](../../../../app/runtime-event-consumption-worker/src/test/java/com/kartaguez/pocoma/runtime/event/consumption/EventConsumptionRuntimePostgresTest.java), [`ProjectionMaterializationConsumptionPostgresTest`](../../../../app/runtime-event-consumption-worker/src/test/java/com/kartaguez/pocoma/runtime/event/consumption/ProjectionMaterializationConsumptionPostgresTest.java), [`CanonicalProjectionTaskRuntimePostgresTest`](../../../../app/runtime-task-consumption-worker/src/test/java/com/kartaguez/pocoma/runtime/task/consumption/CanonicalProjectionTaskRuntimePostgresTest.java), [`BindingRuntimePostgresTest`](../../../../app/runtime-binding-consumption-worker/src/test/java/com/kartaguez/pocoma/runtime/binding/BindingRuntimePostgresTest.java) et [`CurrentBindingPersistencePostgresTest`](../../../../app/infra-read-persistence/src/test/java/com/kartaguez/pocoma/infra/read/persistence/CurrentBindingPersistencePostgresTest.java). Ce sont des preuves partielles ; aucune ne démontre déjà le chaînage Binding Event→Task.

## D. Écart CURRENT_BINDING vers la cible

```text
ACTUEL : autorité Binding → fait durable(event_id,R) → worker Binding → upsert READ CURRENT_BINDING
CIBLE  : autorité Binding → Event durable → worker Event/route → Task(CURRENT_BINDING)
         → worker Task/loader/projector/validation → artifact → vue READ CURRENT_BINDING
```

Le fait Binding existant porte déjà E, R, type, U/B et `event_id` pour décrire l'évolution. Il est un **bon candidat à l'Event source** ; il n'y a aucune nécessité prouvée de produire un doublon dans `business_event_outbox`. En revanche, la découverte actuelle ne le lit pas, sa table code `ATTACHED/DETACHED` sous `fact_type` (sans `EventType` canonical), et la `ProjectionMaterializationCandidate`/task exige une clé cible dont la version est positive. Il faut généraliser la découverte metadata-only et la route explicite pour une troisième source durable, en conservant l'identité `(eventId, CURRENT_BINDING)` du consommateur Event. Une autre modification future de Binding emprunterait alors la même route sans référence à Registration.

Choix de calcul proposé : loader du **fait exact par eventId ou E+R**, plutôt qu'une lecture opportuniste du binding courant, pour produire un snapshot correspondant à la clé de task ; il faut assurer une correspondance durable et non ambiguë entre clé et fait. Une lecture de l'autorité courante pourrait produire R2 pour la task R1 et brouiller provenance/version. `sourceEventId` reste le vrai identifiant du fait, y compris au bootstrap R0. Le projector pur produit un artifact validé. La publication doit aussi avancer la ligne READ monotone par un seul chemin transactionnel/fenced ou définir une vue `latest` sûre sur des roots immutables. Ajouter `CURRENT_BINDING` à `ProjectionWritePort.publish` sans cette règle ne suffit pas. Le root générique et la ligne courante peuvent coexister si leur dual write et leur rattrapage sont démontrés ; la forme finale du store est une décision ci-dessous.

Réutilisables tels quels : politique de routes (après ajout des types), claim/lease/CAS, `ProjectionTaskStorePort.ensure`, orchestrateur Task, catalogue de producteurs, validateur, modèle `ProjectionArtifact`, store de roots immutables. À généraliser : discovery Event (`UNION ALL`), modèle de route/target Binding, configuration des types, mapping de R0 et publication de l'index courant. À supprimer **après cutover prouvé** : découverte directe `JdbcBindingFactDiscoveryAdapter`, `BindingFactConsumptionLocator`, worker/runtime Binding spécialisé et son consumer type, si aucun autre traitement ne les utilise ; conserver les faits et l'autorité. Ne pas faire tourner simultanément l'ancien apply et le nouvel apply sur la même ligne. Backfill depuis les vrais faits, preuve de parité avec V13 et prise en charge des tâches/faits déjà en attente sont indispensables.

## E. Registration : code, cadrage et frontières réelles

`REGISTRATION_REQUEST` **n'existe pas dans `app/`** : aucune classe, table, consumer ou endpoint Registration livré. Le nom codé dans le [canon](Step_Canon.md) est `RegistrationRequest`, avec requestId et identité externe créatrice immuables ; le [plan](Step_Plan.md) prévoit une admission `POST → 202` qui n'écrit que la request, puis un worker spécialisé. Le consumer envisagé `REGISTRATION_REQUEST/requestId + REGISTRATION_PROCESSOR` recharge la request après claim. Son outcome autoritatif, unique par requestId, est `Registered(U,B)` ou `Rejected(EXTERNAL_IDENTITY_ALREADY_USED)` ; failure technique et états Consumption ne sont pas des résultats publics. Une même request rejouée retrouve son outcome ; deux requests concurrentes pour E arbitrent séparément.

Le succès projeté dans le plan crée U, acquiert `Binding(E,U,B)` par l'autorité Binding, écrit l'outcome et les faits `UserCreated(U)` et `ExternalIdentityAttached(E,U,B)` sous la **transaction d'exécution Consumption avec CAS final**. Le POST et ce commit sont séparés. Le fait Attached est déjà append par `JpaExternalIdentityBindingAdapter` dans l'opération d'acquisition envisagée, sans second append Registration. Le commit Event→Task, puis Task→READ, surviendront ensuite séparément. Un rejet de conflit ne crée pas de binding/fait Attached ; il produit seulement l'outcome métier. `UserCreated` est un fait métier distinct, actuellement planifié et absent du code. **Aucun event Binding supplémentaire n'est nécessaire si le fait Attached existant devient source du pipeline Event** ; l'opération `acquireForNewUser` doit cependant être ajoutée au port/adapter primaire et garder l'append dans la transaction. `REGISTRATION_RESULT` est le nom physique proposé pour la représentation READ, non une nécessité conceptuelle.

Le [plan §3.3](Step_Plan.md), actualisé sur le commit distant `01980732`, prévoit désormais un **event terminal de résultat**, puis la route Event→Task `REGISTRATION_RESULT/requestId/1` et un backfill idempotent des outcomes antérieurs. C'est le précédent technique COMMAND_RESULT appliqué à un **résultat d'intention**, distinct de la chaîne `Binding Event→CURRENT_BINDING`. Le même plan introduit REG.0 comme prérequis de normalisation de CURRENT_BINDING. Le [canon §4.1](Step_Canon.md) exige pour un succès une visibilité dépendante de l'occurrence courante exacte `(E,U,B)` et un GET READ seul ; le plan l'implémente via `CURRENT_BINDING`. Cela **couple l'exposition du résultat à la convergence de la projection**, sans coupler le résultat autoritatif lui-même. Un retard ou échec CURRENT_BINDING peut alors retourner 404 malgré un `Registered` déjà committé. Ce comportement doit être distingué explicitement de « la demande a réussi ». Il reste en tension avec l'objectif demandé d'une Request consultable indépendamment de CURRENT_BINDING et doit être arbitré ; l'audit ne réécrit pas D19/D20 en silence.

## F. COMMAND_RESULT comme précédent, avec ses limites

Source : `RecordedCommand(commandId)` admise, puis [`CommandConsumptionExecution`](../../../../app/locator-consumption-command/src/main/java/com/kartaguez/pocoma/locator/consumption/command/CommandConsumptionExecution.java) exécute la demande et publie `Applied/Rejected`; son effet de terminal failure publie `Failed`. [`JdbcCommandOutcomeAdapter`](../../../../app/infra-persistence-jpa/src/main/java/com/kartaguez/pocoma/infra/persistence/jpa/adapter/command/JdbcCommandOutcomeAdapter.java) écrit un outcome unique et un event terminal `COMMAND_APPLIED/REJECTED/FAILED` dans la même transaction ([WRITE V17](../../../../app/infra-persistence-jpa/src/main/resources/db/migration/V17__command_outcomes_and_terminal_events.sql)). Le worker est `runtime-command-consumption-worker` et le CAS Consumption protège ce commit. Ensuite le worker Event route l'event terminal vers une task `COMMAND_RESULT/COMMAND/commandId/1`; le worker Task recharge l'outcome et l'E capturée dans `recorded_commands` ([loader](../../../../app/infra-persistence-jpa/src/main/java/com/kartaguez/pocoma/infra/persistence/jpa/adapter/projection/JdbcCommandResultProjectionInputLoader.java)), projette, valide et publie dans `pocoma_read.projection_root/artifact` ([definition](../../../../app/engine-command-result/src/main/java/com/kartaguez/pocoma/engine/command/result/CommandResultProjectionDefinition.java), [projector](../../../../app/engine-command-result/src/main/java/com/kartaguez/pocoma/engine/command/result/CommandResultProjector.java)). [`GetCommandResultService`](../../../../app/engine-command-result/src/main/java/com/kartaguez/pocoma/engine/command/result/GetCommandResultService.java) lit l'artefact exact et vérifie l'E appelante ; les non-propriétaires reçoivent NotFound. L'outcome primaire et l'artefact READ sont deux commits asynchrones. La clé requestId/commandId et les contraintes uniques donnent corrélation/idempotence ; claim, retry et publication idempotente complètent la protection multi-worker.

**Générique réutilisable pour Registration :** request immuable, outcome autoritatif unique par requestId, corrélation du résultat à l'identité capturée, transaction avec CAS, projection READ éventuelle et GET opaque en cas de non-ownership. **Spécifique Command :** Pot/version, trois états dont `FAILED`, `recorded_commands`, events terminaux Command et `COMMAND_RESULT` JSON. Registration n'a que Registered/Rejected dans son canon ; son éventuel résultat READ peut réutiliser la plomberie ProjectionTask, sans partager le modèle métier Command ni faire de l'outcome la source de CURRENT_BINDING. COMMAND_RESULT utilise la technique de projection pour distribuer un résultat ; sa **sémantique** reste Request/Result, pas une vue de l'état Pot.

## G. Cible consolidée et indépendance

```text
RegistrationRequest R(E) durable (commit admission)
    → worker Registration / claim → outcome(R) + [User, Binding(E,U,B),
      UserCreated, ExternalIdentityAttached] (commit autoritatif + CAS)
       ├→ canal de lecture du résultat R (commit READ ultérieur, corrélé à R/E)
       └→ fait Attached, seulement en cas de mutation Binding
             → Event worker / route CURRENT_BINDING (commit Task ultérieur)
             → Task worker / projector / artifact (commit READ ultérieur)
             → CURRENT_BINDING(E) observable

Autre auteur de Binding → même fait Attached/Detached → même chaîne Event→Task.
```

Le résultat n'est jamais calculé depuis `CURRENT_BINDING`, et CURRENT_BINDING ne lit ni outcome ni request Registration. Registration n'appelle ni `tasks.ensure(CURRENT_BINDING)`, ni son projector. Le retry de Task ne réexécute pas R et ne modifie pas son outcome. Il reste une décision d'API sur la visibilité d'un résultat Registered après détachement : le canon actuel demande un contrôle sur l'occurrence courante READ ; cette règle crée une dépendance de *lecture/visibilité* à CURRENT_BINDING, même si les deux productions sont indépendantes. Une éventuelle révision de cette règle doit préserver l'ownership par E exacte et l'absence de transfert vers B2.

## H. Écarts et risques classés

1. **Bloquant — chaîne absente.** Les faits Binding ne sont pas une source du worker Event ; sans généralisation de la discovery et de la route, aucune Task CURRENT_BINDING ne naît. Ajouter seulement un projector ne sert à rien.
2. **Bloquant — forme de sortie.** `projection_root/artifact` immutable ne remplace pas automatiquement l'upsert courant monotone ; publication tardive de R ancien, double écriture et parité du cutover demandent une preuve transactionnelle.
3. **Bloquant — clé R0.** La baseline factuelle R0 est légitime, mais `ProjectionKey`/task/root exigent ≥1 ; ne pas inventer de fact ni fusionner R0 et R1 sous la même clé.
4. **Élevé — visibilité Registration en tension.** Le plan actualisé choisit correctement un event terminal de résultat et REG.0 comme prérequis. Son GET succès reste conditionné par CURRENT_BINDING : la consultabilité dépend du lag/failure de cette projection, contrairement à l'indépendance demandée.
5. **Élevé — cutover et doublons.** Deux workers écrivant la vue, ou des facts historiques non repris, peuvent diverger. V12/V13 et les tests actuels aident mais ne couvrent pas le nouveau pipeline.
6. **Élevé — transactions asynchrones.** Aucun schéma ou test ne doit promettre une publication READ atomique avec l'outcome Registration ou le fait Binding. Le commit autoritatif est la seule frontière commune du succès métier.
7. **Moyen — placement des modules.** La [révision engines](../ARCHITECTURE/Three_Engine_Families_Revision.md) prévoit `engine-consumption-event` pour route/discovery, `engine-consumption-projection-task` pour orchestration, `projection-current-binding` pour le producteur, `engine-read-binding` pour la requête, et `engine-write-registration`/`engine-consumption-registration` pour R. C'est compatible avec la cible et avec le REG.0 désormais inscrit au plan. Le runtime Binding spécifique devient candidat à suppression, ce qui impose un gate architectural lors du changement réel des modules.

## J. Décisions architecturales encore nécessaires

1. **Représentation standard de R0 :** version technique `R+1`, clé par eventId avec version 1, ou autre encodage injectif ; démontrer stabilité, lecture exacte et compatibilité avec R1.
2. **Publication CURRENT_BINDING :** roots immutables plus index courant monotone, ou lecture du dernier root validé ; fixer atomicité, gestion des failures et contrat de GET. La continuité de R du binding primaire ne doit pas être confondue avec la version du root.
3. **Event terminal Registration :** le plan actualisé choisit la route Event→Task, comme Command ; restent à fixer son schéma durable, sa clé, sa transaction avec l'outcome et le backfill des outcomes antérieurs. Cette technique n'en fait pas une projection d'état.
4. **Visibilité de `Registered` :** maintenir D19 avec 404 si CURRENT_BINDING READ tarde/échoue, ou réviser le canon pour un résultat consultable par l'auteur dès sa matérialisation, avec une règle distincte de révocation/occurrence. L'objectif d'indépendance impose une décision explicite ; ne pas résoudre via lecture opportuniste du primaire dans le GET.
5. **Séquence de migration :** modalité de drain/backfill des faits et des slots Binding existants, contrôle de parité, puis suppression de l'ancien worker sans fenêtre de perte ni double écriture. La preuve doit couvrir les faits R0 de migration.
