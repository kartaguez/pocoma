## E. Graphe des dépendances internes

Les 175 arcs sont déclaratifs, pas une preuve que chaque dépendance est nécessaire au code. Le tableau C contient les arcs directs exhaustifs. Vue compacte des directions importantes :

```text
domain-* / authentication-contracts
  -> engine-* / orchestrator-command-admission / orchestrator-consumption
  -> locator-* / supra-* / infra-* (selon les ports)
  -> runtime-* (neuf racines de déploiement)

engine-projection-task -> engine-consumption
orchestrator-consumption -> engine-consumption + engine-projection-task
engine-command-result -> engine-command
engine-registration -> domain-user-identity + engine-core
infra-persistence-jpa -> 18 modules internes de domaine/application/infra
9 runtimes -> infra-persistence-jpa
```

Fan-in direct maximal : `domain-pot` 11 ; `orchestrator-consumption`, `infra-tx-spring`, `infra-persistence-jpa`, `domain-user-identity`, `domain-projection` 9 chacun ; `supra-consumption-worker` et `engine-core` 8. Un fan-in élevé peut être normal pour un contrat partagé ou un adapter commun. Les seules feuilles de production sont les neuf runtimes ; `architecture-tests` n'a que des dépendances de test. Aucun `engine-*` n'importe de package runtime ou JPA/Spring dans `src/main` selon le scan d'imports ; `infra-persistence-jpa` dépend, lui, de nombreux ports applicatifs. Le gros module fait donc monter la fermeture Maven de chaque runtime même lorsque celui-ci n'utilise qu'une fraction de ses adapters.

Arcs à expliquer plutôt qu'à condamner : `orchestrator-consumption → engine-projection-task` est porté par `ProjectionTaskConsumptionOrchestrator`, spécialisation Task dans le module générique ; `engine-command-result → engine-command` donne accès à `CommandId` et `CommandOutcome` pour matérialiser **et lire** le Result ; `infra-persistence-jpa → orchestrator-command-admission` et `supra-http-read-query → orchestrator-command-admission` demandent une revue des types réellement importés ; `engine-read-projection` est partagé par Binding et LKV sans contrat de lecture commun. Aucune de ces observations n'autorise seule un déplacement.

## G. Consumption, locators et loaders

`domain-consumption` possède les identités, claims, leases, états et provenance ; `engine-consumption` les use cases d'acquisition, exécution, finalisation, failure/retry et wrappers transactionnels. Aucun n'est propriétaire de Command, Event, Binding ou Result au sens métier. **Hypothèse « Consumption = infrastructure d'exécution réutilisable » confirmée pour ce noyau**, avec contre-exemple de placement : `orchestrator-consumption` héberge `ProjectionTaskConsumptionOrchestrator` spécifique, et certains runtimes hébergent des policies spécialisées.

`SequentialConsumptionOrchestrator` parcourt un candidat à la fois, acquiert, ferme le search, appelle `ExecuteConsumptionUseCase` et classe l'échec après rollback. Command, Registration, les deux Results, Binding et LKV l'emploient. `AcquireThenFinalizeConsumptionOrchestrator` parcourt des pages, acquiert, laisse une préparation se faire après la transaction d'acquisition, puis appelle un finalizer fenced. Event→Task et Task en sont les usages ; Task force une nouvelle page après acquisition. Dans les deux formes, le commit de claim est distinct du commit d'effet ; le CAS final empêche un ancien claim de publier un effet durable. Les modes diffèrent quant à la durée de préparation, à l'emplacement de l'effet et à la classification des échecs ; aucune interchangeabilité ou `Processor<T>` universel n'est démontrée. [Orchestrateurs](../../../../app/orchestrator-consumption/src/main/java/com/kartaguez/pocoma/orchestrator/consumption/SequentialConsumptionOrchestrator.java), [transaction](../../../../app/engine-consumption/src/main/java/com/kartaguez/pocoma/engine/service/transaction/consumption/TransactionalExecuteConsumptionUseCase.java).

Asymétries à conserver comme faits : Command découvre un ID et recharge la request autoritaire ; Event→Task utilise les métadonnées sans EventLoader ; Binding découvre puis recharge le fact par `eventId` ; Command Result confronte Event/outcome/Command ; Registration Result recharge request/outcome ; Task porte déjà sa `ProjectionKey` et ses **ProjectionInputLoader** propres aux producteurs chargent les données historiques. Elles répondent à des sources et garanties différentes. Aucune duplication artificielle n'est démontrée par la seule absence d'un Loader homonyme.

## I. Zones mixtes et frontières physiques

**`engine-core`** contient 18 fichiers Java de production (dont `package-info`) : `TransactionRunner`, snapshots Pot/Expense et version Pot, `RecordedEvent` et envelope/trace, `WorkerSegment`/hash/partition, `UserContext`, exceptions. Il n'exécute pas une capacité unique. Sa frontière actuelle garde ces contrats partagés sans Spring/JPA et évite aux consommateurs de dépendre directement d'un runtime ou d'un adapter ; elle est utile au niveau de dépendance, mais sa cohérence fonctionnelle est partielle. Huit modules l'importent directement, notamment Consumption, Registration, Event, Pot Command, transactions Spring et admission. Le mot « core » masque cette hétérogénéité ; cela n'est pas une preuve qu'un split serait bénéfique.

**`infra-persistence-jpa`** compte 72 classes de production et 18 dépendances internes directes. Il couvre Pot/Expense WRITE, outbox Event, Command request/outcome/terminal, Consumption slots/claims/provenance, Binding autorité/stream/facts/discovery, Registration request/outcome/facts, Results Command/Registration, découverte Event/Task/LKV et loaders historiques pour les projections Pot. Les packages `adapter/{command,consumption,core,identity,outbox,processing,projection,registration}` et `repository/{command,consumption,core,identity,outbox}` rendent ces responsabilités observables. Les neuf runtimes en dépendent directement. Le module protège la direction application→ports←persistence et évite JPA dans les engines ; il agrège toutefois des adapters de capacités et bases logiques distinctes. Le coût de sa fermeture Maven est réel, mais aucune nécessité de scission n'est prouvée sans analyse des transactions et consommateurs.

**`engine-command-result`** contient le contrat `ImmutableCommandResult`/store, le contrôle de cohérence et la matérialisation, le GET, son contrat public et l'ownership historique. Il dépend de `engine-command` pour `CommandId`/`CommandOutcome`. La discovery, le reload SQL et le store concret sont dans le runtime et `infra-persistence-jpa`; la classification et le retry sont dans `CommandResultConsumptionLocator` du runtime. La frontière fonctionnelle « Command Result » existe ; elle réunit néanmoins production et query, tandis que la mécanique spécialisée se répartit sur trois modules. La dépendance de son GET envers le module Command mérite d'être expliquée au niveau des types, sans présumer de correction.

**`engine-registration`** réunit admission WRITE, request/outcome, exécution User/Binding, ports, materialization et GET Result. Il dépend seulement de `domain-user-identity` et `engine-core`, non de `engine-consumption` ; le runtime assemble le protocole. C'est une bonne protection contre la dépendance de l'exécution métier au polling, tout en étant un module fonctionnel multi-rôles. Les deux locators Registration et Result, leurs policies et le wiring vivent dans leurs runtimes ; les stores et discovery dans `infra-persistence-jpa`.

**Projection** : `engine-projection-contracts` définit des ports neutres READ/WRITE ; `engine-projection-read` lit exactement une projection ; `engine-pot-read` interprète AUTH et READ_POT et décide l'accès ; `engine-projection-pot` et `engine-projection-balance` portent loaders abstraits, calcul et projectors ; `engine-projection-task` porte aussi catalog, Task, préparation, retry et consommation ; `engine-read-projection` réunit deux sujets distincts, LKV et Current Binding, plus contrat de reconstruction Pot historique. Le préfixe `engine-` n'est donc pas un rôle architectural fiable. Les projectors inspectés ne portent ni SQL ni Spring ; `ProjectionValidator` valide la sortie. L'orchestration Task spécialisée se trouve en revanche dans `orchestrator-consumption`, et la table de routage Event dans un runtime.

**GET Pot** : le franchissement PRIMARY n'est pas dans `ReadPotService` mais dans `supra-http-read-query/PotQueryController`, qui dépend du port `ExternalIdentityResolverPort` de `domain-user-identity` et du `TransactionRunner` d'`engine-core`. L'implémentation `JpaExternalIdentityResolverAdapter` est dans `infra-persistence-jpa` et lit l'autorité externe. Le runtime Web assemble les deux. C'est une dépendance de lecture HTTP vers un port d'autorité primaire, et une limite de modularité READ constatée ; sa cible reste ouverte.

Frontières clairement observables : modèles `domain-*` sans Spring/JPA ; noyau Consumption sans capacités métier ; interface transactionnelle `engine-core`/`infra-tx-spring` ; interfaces de projection et adapters SQL ; couche HTTP `supra-*` ; séparation des processus runtime ; séparation du Result et du Binding courant dans deux consumers indépendants. Frontières **à challenger** : utilité physique propre d'`authentication-contracts`, `binding-pot-command-spring`, `infra-projection-json-schema`, certains petits `locator-*` et de plusieurs modules `engine-projection-*` ; leur taille ou leur fan-in ne conclut rien. Pour chacun, il faut identifier l'import interdit effectivement bloqué, et vérifier le graphe transitif et les tests avant qualification « administrative ».

The old `engine-command-result` module is removed. `engine-registration` now retains only WP3 legacy execution/request/outcome compatibility, with no Result materialization/read policy. `supra-http-write` and `supra-http-read` own the HTTP endpoints; `runtime-web-api` composes them and owns the concrete Spring Security provider. `engine-read-pot` now performs the existing PRIMARY-backed E→U resolution before exact AUTH@V/READ_POT@V reads. This is a WP4 delta to the baseline audit above, not a rewrite of its historical 51-module observation. `TBD-E2U` and `TBD-COMMAND-CONTRACT` remain OPEN; the latter has an explicit post-WP4 checkpoint in the migration plan.
