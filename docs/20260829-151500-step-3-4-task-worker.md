# Étape 3.4 — `supra-worker-task` et actualisation de la roadmap 3–7

## Résumé

Créer le worker pull Task cible :

```text
SingleItemPullLoop
→ ClaimNextTaskUseCase
→ ExecutionGuard<taskId>
     └── RecordedTaskExecutionMapper
         → ExecuteTaskUseCase
→ CompleteTaskProcessingUseCase
```

Une instance est liée à un `PipelineDefinition` et un `WorkerSegment`. Elle traite une seule Task à la fois, sans préfetch, heartbeat ou retry automatique.

Avant le code, archiver ce plan et actualiser `docs/20260828-234057-step-3-plus-roadmap.md` avec le `ConsumptionSlot` autoritatif, les statuts Command/Task réconciliables, les guards Command/Task, l'idempotence Event vers Tasks, l'unicité PostgreSQL des claims actifs, l'invariant de lease sans heartbeat, l'`Idempotency-Key` HTTP par utilisateur et les workers Command, Event et Task actualisés.

## Settings et lifecycle

`TaskWorkerSettings` contient :

```java
boolean enabled
String workerId
Duration pollingInterval
Duration leaseDuration
Duration maxNormalProcessingDuration
WorkerSegment segment
PipelineDefinition pipeline
boolean wakeSignalsEnabled
```

Valider `leaseDuration >= 3 × maxNormalProcessingDuration`.

Le worker expose `start()`, `stop()`, `isRunning()` et `runOnce()`.

Après claim :

- arrêt avant le guard : release ;
- arrêt pendant le callback : ne pas interrompre et ne pas release ;
- polling toujours disponible ;
- signal optionnel `TASK_AVAILABLE` ;
- wake désactivé par défaut au futur wiring.

## Mapping durable vers typé

Définir :

```java
public interface RecordedTaskExecutionMapper<T extends TaskPayload> {
    PipelineDefinition pipeline();
    String taskType();
    Class<T> payloadType();
    ExecuteTaskInput<T> map(RecordedTask task);
}
```

Le registre route par pipeline/version/type, rejette les doublons, distingue les versions, valide la cohérence de l'input produit, lève `RecordedTaskMappingException` avec un code stable et n'expose jamais le JSON ou un identifiant dans ses messages.

Codes initiaux :

```text
MISSING_TASK_MAPPER
INVALID_TASK_PAYLOAD
INCONSISTENT_MAPPED_PIPELINE
INCONSISTENT_MAPPED_TASK_TYPE
INCONSISTENT_MAPPED_PAYLOAD_TYPE
```

Les codecs restent dans les implémentations runtime de pipeline. Aucun Jackson n'entre dans le nouveau worker.

## Guard et exécution

Le mapping et l'exécution sont placés dans le callback du guard :

```java
executionGuard.executeOnce(taskId, () -> {
    ExecuteTaskInput<?> input = mapperRegistry.map(recordedTask);
    executeTaskUseCase.executeTask(input);
});
```

Conséquences : première exécution = mapper puis handler ; `ALREADY_EXECUTED` = ni mapper ni handler ; une erreur du callback rollbacke journal et effet ; une erreur du guard ou du commit constitue une issue inconnue sans transition technique ; le reclaim suivant consulte à nouveau le journal.

Ajouter `TaskExecutionRejectedException` dans task execution typée, uniquement pour un refus fonctionnel déterministe et non retryable.

## Classification des erreurs

Créer :

```java
public interface TaskProcessingFailureClassifier {
    Optional<ProcessingFailure> classify(Throwable failure);
}
```

Classification par défaut :

- payload durable définitivement invalide : `INVALID_TASK_PAYLOAD` ;
- `TaskExecutionRejectedException` : `TASK_EXECUTION_REJECTED` ;
- mapper ou handler absent : erreur technique ;
- type Java incohérent : erreur technique ;
- persistence, transaction ou commit : erreur technique ;
- exception inconnue : erreur technique.

Une failure classifiée appelle `FailTaskProcessingUseCase`. Une erreur technique ne provoque ni fail, ni complete, ni release : elle est observée et propagée, puis le claim expire.

## `ConsumptionSlot` autoritatif

Le worker ne réconcilie jamais directement les Tasks. `ClaimNextTaskUseCase` absorbe :

```text
Acquired         → TaskClaimResult
NotAcquiredBusy  → candidat suivant
AlreadyCompleted → TaskPort.markCompleted → candidat suivant
AlreadyFailed    → TaskPort.markFailed avec la failure historique → candidat suivant
```

Une Task avec slot terminal n'atteint donc jamais le worker, le mapper, le guard ou le handler.

Complete/fail respecte :

```text
transition autoritative du slot
→ commit
→ matérialisation best effort du statut Task
```

Aucun décorateur transactionnel spécialisé complete/fail Task n'est recréé.

## Observation

Outcomes :

```text
IDLE
EXECUTED_AND_COMPLETED
ALREADY_EXECUTED_AND_COMPLETED
TASK_EXECUTION_FAILED
RELEASED_BEFORE_EXECUTION
OWNERSHIP_LOST
TECHNICAL_ERROR
LEASE_WARNING
LEASE_EXCEEDED
```

Une observation contient seulement outcome, durée, lease, pipeline et segment. Aucun identifiant métier, token, type ou payload.

Seuils : `durée >= 80 % lease → LEASE_WARNING` et `durée >= lease → LEASE_EXCEEDED`.

## Tests

Tester le registre : routage pipeline/version/type, versions indépendantes, doublons refusés, mapper absent, payload invalide et sorties incohérentes.

Tester l'itération : idle, exactement une Task, `EXECUTED` puis complete, `ALREADY_EXECUTED` sans mapper ni handler, release avant exécution, failure classifiée, erreur technique sans transition, ownership lost et erreurs de complete/fail/release sans compensation.

Tester le crash :

```text
handler + journal commit
→ complete échoue
→ lease expire
→ reclaim
→ ALREADY_EXECUTED
→ complete avec nouveau token
```

Vérifier que l'effet n'est appliqué qu'une fois.

Tester la réconciliation :

```text
Task PENDING + slot COMPLETED
→ statut terminal sans worker, mapper, guard ou handler

Task PENDING + slot FAILED
→ failure historique matérialisée sans exécution
```

Tester concurrence et lease : sérialisation dans une instance, parallélisme entre instances, même Task jamais exécutée simultanément, warning et dépassement de lease, ancien token fenced et aucun heartbeat.

ArchUnit interdit au worker les ports sortants et repositories, `ConsumptionKey`, la dépendance directe à `engine-consumption`, les packages legacy, les frameworks et codecs, et la réconciliation directe.
