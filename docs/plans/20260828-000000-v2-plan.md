Plan de migration
Phase 0 — garde-fous architecturaux
Objectif : fixer les frontières avant tout déplacement.
Concernés :
- tous les pom.xml ;
- packages engine-*, supra-*, infra-*.
À créer :
- module de tests architecture-tests ou tests ArchUnit dans le parent ;
- règles de dépendance.
Tests :
- domain-* ne dépend de rien côté Spring/JPA/worker ;
- application-* ne dépend pas d’infra/supra/runtime ;
- infra-* ne dépend pas de supra-* ;
- worker-* dépend des ports entrants/processing uniquement ;
- aucun package application n’importe claimable.polling, Spring ou JPA.
Terminé lorsque les règles reflètent d’abord les exceptions existantes explicitement listées et empêchent toute nouvelle dérive.
Phase 1 — formaliser les use cases métier sans les déplacer
Objectif : documenter et verrouiller le noyau réutilisable.
Concernés :
- toutes les commands/interfaces/services/contextes de engine-pot-command ;
- engine-query ;
- ComputePotBalancesUseCase/Service.
À créer :
- tests contractuels « invocation directe sans worker » ;
- fakes in-memory des ports Pot/Event ;
- éventuellement BusinessCommandHandler uniquement comme marqueur, sans dispatcher.
À déplacer/supprimer : rien.
Tests :
- chaque command use case avec fakes, sans Spring/JPA ;
- chaque query avec fake query port ;
- émission des bons événements ;
- conflit optimistic concurrency inchangé.
Terminé lorsque chaque use case métier peut être construit et exécuté en Java pur.
Phase 2 — introduire les objets de processing communs
Objectif : séparer ownership technique et payload fonctionnel.
À créer dans application-processing :
- ClaimToken, WorkerId, ClaimLease, ProcessingStatus ;
- ClaimedCommand, ClaimedEventProcessing, ClaimedTask ;
- contrats explicites claim/complete/fail/release.
À déplacer :
- sémantique de PipelineTaskStatus vers processing ;
- critères de claim aujourd’hui dans supra vers application.
À modifier :
- domain-pipeline-tasks ;
- engine-task-execution ;
- infra-persistence-jpa/pom.xml.
À supprimer :
- PipelineTaskClaim après remplacement ;
- token embarqué dans PipelineTask.
Tests :
- invariants de ClaimToken ;
- impossible de construire un Claimed* sans token ;
- application-processing sans Spring/JPA.
Terminé lorsque Task et claim sont deux objets séparés et que l’infra ne dépend plus des supras pour leurs contrats.
Phase 3 — stabiliser Event → Task pur
Objectif : isoler ProcessEventForPipeline.
À créer :
- ProcessEventForPipelineUseCase ;
- ProcessEventForPipelineCommand ;
- EventProcessingOutcome;
- balance EventPipelineProcessor;
- CreateTasksForEventPort.
À modifier :
- PipelineStrategy, PipelineRegistry ;
- MaterializeTasksService ;
- TaskDescriptor.
À déplacer :
- PipelineDefinition, PipelineId, TaskDescriptor vers application event/task.
À supprimer ultérieurement :
- méthodes markSkipped/markFailed du port fonctionnel.
Tests :
- événement supporté → 0, 1 ou N Tasks ;
- événement non supporté → résultat explicite, pas exception technique ;
- deux pipelines reçoivent le même Event indépendamment ;
- exception du processor remonte au worker au lieu d’être convertie implicitement en statut.
Terminé lorsque le use case ne connaît ni claim, ni worker, ni statut durable.
Phase 4 — transformer le registre Event × Pipeline en queue claimable
Objectif : implémenter le claim indépendant par pipeline.
Migration SQL additive :
- enrichir event_4_pipeline_materialization_status, ou créer event_processing, avec :
  - READY, CLAIMED, DONE, FAILED ;
  - claim_token, claimed_by, lease_until ;
  - timestamps et attempts ;
  - unique (event_id,pipeline_id,pipeline_version).
À créer :
- JpaEventProcessingStore;
- requêtes claimNext, complete, fail, release.
À modifier :
- création des unités READY lors de l’arrivée d’un Event ou par reconciliation/backfill ;
- JpaPipelineMaterializationAdapter.
Tests PostgreSQL/Testcontainers :
- claim atomique avec deux transactions ;
- un seul gagnant ;
- reclaim après expiration avec nouveau token ;
- ancien token incapable de complete/fail/release ;
- Pipeline A en échec n’empêche pas Pipeline B ;
- création Tasks + complete processing atomiques.
Terminé lorsque chaque couple Event/Pipeline dispose d’un lifecycle fenced indépendant.
Phase 5 — créer l’EventWorker simple
Objectif : remplacer le materializer batch par un orchestrateur 1-at-a-time.
À créer :
- EventWorker;
- EventWorkerLifecycle;
- EventWorkerSettings;
- petite WorkerLoop.
Flux :
claimNextEventProcessing()
→ ProcessEventForPipeline
→ create tasks
→ complete(token)
ou fail/release(token)
À modifier :
- runtime task materialization ;
- Spring configuration et métriques.
À ne pas réutiliser :
- ClaimableWorkDispatcher ;
- SegmentedWorkerPool.
Tests :
- au plus un processing actif dans une instance ;
- aucun deuxième claim avant complete/fail ;
- worker arrêté proprement ;
- exception → fail/release avec le token courant ;
- aucun processor métier dans le worker.
Terminé lorsque batchSize, queueCapacity, threadCount et segmentation Pot ne sont plus nécessaires à ce worker.
Phase 6 — simplifier Task execution
Objectif : faire de TaskWorker un orchestrateur pur.
À créer :
- TaskWorker;
- use cases techniques Task explicites ;
- ExecuteBalanceProjectionTaskUseCase ou handler équivalent.
À modifier :
- PipelineTaskExecutorWorker;
- ExecutePipelineTaskService;
- ComputeBalancesPipelineTaskExecutionStrategy;
- JpaPipelineTaskWorkSourceAdapter.
Tests :
- bonne sélection par pipeline/version/taskType ;
- handler erroné jamais appelé ;
- un worker, une Task active ;
- deux instances traitent deux Tasks en parallèle ;
- mauvais token ne complète pas ;
- handler testable sans DB/worker ;
- idempotence balance pour la même version.
Terminé lorsque la nouvelle table tasks_4_pipeline est l’unique queue du pipeline balance générique.
Phase 7 — migrer la projection balance vers le nouveau pipeline
Objectif : retirer le doublon ancien.
Déroulement :
1. activer le pipeline balance générique en shadow mode ;
2. vérifier les Tasks produites ;
3. activer l’exécution sur une projection de test ou avec garde d’idempotence ;
4. comparer version et balances ;
5. basculer ;
6. désactiver anciens workers.
À supprimer après observation :
- BuildProjectionTasksUseCase/Service;
- ExecuteProjectionTasksUseCase/Service;
- anciens workers projection ;
- ProjectionTaskPort, modèles et table projection_tasks;
- runtimes anciens.
Tests :
- parcours Event → Task → balances ;
- comparaison ancien/nouveau sur historique ;
- reprise après crash ;
- backlog drainé par plusieurs workers.
Terminé lorsque projection_tasks ne reçoit plus d’écriture et que les métriques du nouveau pipeline sont stables.
Phase 8 — ajouter la Command durable
Objectif : introduire le premier buffer de la chaîne.
À créer :
- StoredCommand/CommandEnvelope;
- type, schema version, payload, actor/scopes, trace, idempotency key ;
- SubmitCommandUseCase;
- CommandStore;
- table commands;
- JPA entity/repository/adapter ;
- codecs explicites pour les dix command types.
Contraintes SQL :
- id primaire stable ;
- index claimable ;
- idempotency key optionnelle mais recommandée ;
- lifecycle et token identiques aux autres traitements.
Tests :
- round-trip de chaque payload ;
- compatibilité de version du codec ;
- soumission durable sans exécution ;
- duplicate idempotency key ;
- atomic claim et fencing.
Terminé lorsque HTTP peut persister une Command sans exécuter le métier.
Phase 9 — créer le CommandWorker
Objectif : exécuter les mêmes use cases métier depuis la queue.
À créer :
- CommandWorker;
- résolveurs/handlers explicites par type de Command ;
- runtime dédié.
Le handler :
- décode l’enveloppe ;
- reconstruit UserContext ;
- appelle exactement le use case métier existant.
Tests :
- chaque type durable appelle le bon use case ;
- le use case testé est identique au mode push ;
- worker ne contient aucune règle métier ;
- transaction métier écrit état + Event outbox ;
- complete Command seulement après succès ;
- conflit de version classifié selon la politique retenue.
Terminé lorsque CommandWorker traite un élément à la fois et produit les mêmes effets qu’un appel direct.
Phase 10 — rendre HTTP push/pull configurable
Objectif : démontrer l’indépendance du déclenchement.
À créer :
- CommandSubmissionFacade ou deux configurations :
  - AsyncCommandControllerAdapter;
  - wiring direct existant pour push.
À modifier :
- command controllers ;
- DTO de réponse asynchrone ;
- OpenAPI ;
- tests HTTP.
Tests contractuels :
- même intention en push et pull → même état métier et mêmes Events ;
- pull retourne 202 + commandId ;
- push conserve la réponse fonctionnelle ;
- changement de mode limité au wiring/supra.
Terminé lorsque les modules command métier sont strictement identiques dans les deux runtimes.
Phase 11 — nettoyer le framework et les anciens modules
Objectif : terminer la migration sans conserver deux architectures.
À supprimer si plus référencés :
- orchestrator-claimable-work-dispatcher sauf une éventuelle boucle minimale ;
- shared-supra-dispatcher-projection ;
- quatre anciens modules de projection/dispatch ;
- anciennes tables et métriques ;
- doublons de configuration dans runtime-monolith.
Terminé lorsque le graphe Maven respecte les règles ArchUnit et qu’aucune infrastructure ne dépend d’un supra.
