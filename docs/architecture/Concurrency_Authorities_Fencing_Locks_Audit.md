# Audit des autorités de concurrence, du fencing et des locks pessimistes

Date : 2026-10-06. Périmètre : code de production du checkout `feat/runtime-monolith` à `f9981eb4af3f83f3101f581eb715fa6572cb0036`, migrations courantes et tests pertinents. Les propositions ci-dessous ne décrivent aucun changement réalisé.

## A. Synthèse

Les autorités WRITE principales sont la version globale par Pot, le couple **stream de Binding + ligne active** par identité externe et le slot de Consumption par couple consommable/consumer. Les Commands, Events, Binding facts, outcomes et résultats publiés sont des journaux ou valeurs immuables arbitrés par PK/UNIQUE. `CURRENT_BINDING`, la Latest Known Version et les projections sont des états dérivés ; ils ne décident pas de la légitimité d'une mutation WRITE.

La recherche de `FOR UPDATE`, `PESSIMISTIC_WRITE`, `@Lock`, advisory locks et mutex applicatifs dans le code de production a trouvé **trois sites SQL `FOR UPDATE`**, correspondant à **quatre usages métier** : acquisition de slot, finalisation avec effet, reprise d'une Command après perte du fence Binding, et mutation du stream Binding (Acquire et Detach). Classification de ces quatre usages : **P1 0, P2 1, O1 3, O2 0, O3 0, UNKNOWN 0**. Le P2 est Binding. Cette classification évalue une alternative possible, pas l'autorisation de retirer le lock actuel. Aucun lock ne peut être supprimé isolément sans altérer une garantie actuelle.

Aucun trou de fencing **démontré** dans les chemins SQL inspectés. Le `claimId` courant et le fence Binding tardif arrêtent les anciens acteurs au commit ; les effets durables examinés participent à la transaction correspondante. La preuve dynamique complète reste limitée : la slice BINDING échoue dans cinq tests runtime à l'injection de deux beans `TransactionRunner`. Le test PostgreSQL de la sémantique `NOT EXISTS` passe et **réfute** une variante naïve de fence optimiste. Les extensions futures du port `FencedDurableEffect` ou des écritures hors de la transaction SQL demanderaient une preuve distincte.

Le plus petit point de sérialisation est normalement **un Pot**, **une identité externe E**, **un slot de Consumption**, **une clé de projection**, ou **un ID de résultat**. Rien dans le code inspecté n'exige une section critique globale. Les écritures touchent souvent plusieurs tables, mais cela ne prouve pas qu'elles demandent plusieurs autorités indépendantes : leur commit atomique et une autorité d'arbitrage sont deux exigences différentes.

## D. Fiches des locks pessimistes

### L1 — Acquisition et reprise d'un slot

**Lieu et transaction.** `JpaConsumptionSlotRepository.findByKeyForUpdate`, appelé par `JpaConsumptionLifecycleAdapter.acquire` (`MANDATORY`), lui-même exécuté dans la transaction d'acquisition du worker. Chaîne : `INSERT slot ON CONFLICT DO NOTHING` → lock du slot par clé → décision DONE/NotReady/Busy/takeover → invalidation de l'ancien claim si lease expirée → insert nouveau claim → `installClaim` → commit. Le verrou couvre un slot, pas un stream d'Event ou un Pot.

**Invariant et race.** Un slot PENDING a au plus un `current_claim_id`, ses `attempt_number` ne se répètent pas et une lease expirée ne perd son autorité qu'au takeover committé. Sans lock : T1 et T2 lisent `last_attempt_number=3`, claim expiré C3 ; T1 invalide C3 et crée C4/attempt 4 ; T2 essaie la même invalidation et attempt 4. Les conditions/UNIQUE actuels provoquent au mieux un rollback technique ; si seul le verrou est ôté, la décision `Busy`/takeover et les garanties de progression ne sont plus exprimées correctement. L'autorité logique est le slot ; la ligne claim est un historique subordonné, écrit dans le même commit.

**Classe O1.** Alternative exacte à prouver : lire `(slot_id,revision,current_claim_id,last_attempt_number,next_claim_at)` et la lease ; insérer le nouveau claim `(claimId,slot,n+1)` puis `UPDATE consumption_slots SET current_claim_id=:new, last_attempt_number=:n+1, revision=revision+1 WHERE slot_id=:id AND revision=:read AND status='PENDING' AND current_claim_id IS NOT DISTINCT FROM :old`, avec condition temporelle validée, puis invalider l'ancien claim dans **la même transaction**. L'insertion précède l'UPDATE car la FK `(slot_id,current_claim_id)` pointe vers la ligne claim. Le loser rollbacke aussi son claim inséré et relit dans une nouvelle transaction ; crash avant commit ne laisse aucun claim installé. `claimId` nouveau reste le fencing token, `revision` évite ABA, UNIQUE `(slot,attempt)` reste garde secondaire. La lecture de lease doit être revalidée contre une mutation concurrente de cette lease ; aujourd'hui la lease du claim n'est pas prolongée. Cette alternative fonctionne entre instances si **tous** les writers de slot suivent le CAS.

### L2 — Finalisation avec effet durable

**Lieu et transaction.** `JpaConsumptionSlotRepository.findByIdForUpdate` via `lockCurrentClaim` ; `FinalizeConsumptionService`, enveloppé par `TransactionalFinalizeConsumptionUseCase`. Utilisé notamment par EVENT pour `ensure(ProjectionTask)` et par PROJECTION pour `publish`/`recordFailure`. Chaîne : lock slot → vérifier claim courant → effet durable SQL → `terminalize` ou `handleFailure` conditionné par claim → commit. L'effet de projection passe par `JdbcProjectionStoreAdapter` et un `TransactionTemplate` du manager injecté ; l'atomicité effective dépend de ce même manager/datasource dans le runtime.

**Invariant et race.** Un worker qui a perdu le claim ne peut publier ni tâche ni projection. Sans lock **et sans autre changement** : T1 lit C1 courant ; sa lease expire ; T2 prend C2 et committe ; T1 effectue `ensure`/`publish` avant `terminalize(C1)` qui retourne zéro. Si l'effet peut committer séparément, l'ancien acteur laisse un effet ; dans une seule transaction, l'échec doit obligatoirement rollbacker l'effet. Le lock actuel fixe l'ordre avant l'effet et empêche T2 de remplacer C1 jusqu'au commit de T1. Une seule autorité d'arbitrage, le slot, même si plusieurs tables sont écrites.

**Classe O1.** Faire **d'abord** un `UPDATE consumption_slots SET revision=revision+1 WHERE slot_id=:id AND status='PENDING' AND current_claim_id=:claimId AND revision=:read` ; si zéro, ne pas exécuter l'effet ; si un, exécuter l'effet et terminaliser dans le même commit. Le `claimId` fence, la révision interdit ABA. Le loser peut réacquérir selon la policy ; après crash, rollback total ou slot terminal + effet durable. Entre instances, l'`UPDATE` gagne le row lock SQL jusqu'au commit : retirer le `SELECT FOR UPDATE` ne retire pas toute sérialisation. Un effet externe non transactionnel n'est pas couvert par cette preuve et requerrait son propre fencing/idempotence.

### L3 — Recovery d'une Command après échec du fence Binding

**Lieu et transaction.** `BindingFenceRecoveryExecuteUseCase.execute` ouvre une nouvelle transaction après rollback du travail Command, appelle `lifecycle.lockCurrentClaim`, lit `bindings.findUserId(E,B)`, puis réexécute un chemin qui publie `Rejected(CALLER_IDENTITY_NOT_CURRENT)` et terminalise le claim. Le même repository `findByIdForUpdate` est utilisé par L2, mais l'usage et la décision sont distincts.

**Invariant et race.** Un ancien claim ne peut publier un rejet terminal après sa reprise. Sans lock : T1 vérifie C1, T2 installe C2, T1 publie le rejet puis échoue à terminaliser C1. Le rollback transactionnel doit effacer le rejet ; la vérification préalable verrouillée garantit aussi qu'aucun nouveau claim ne gagne pendant la décision. L'autorité terminale est le slot ; la lecture Binding répond à une autre question, celle de la présence du B exact.

**Classe O1 avec réserve de composition.** Un `UPDATE slot SET revision=revision+1 WHERE slot_id=:id AND current_claim_id=:claimId AND status='PENDING' AND revision=:read` avant la publication remplace le verrou préalable, dans la transaction de recovery. `claimId` fence ; si zéro, abandonner et relire/retry sans issue durable. Conserver la terminalisation conditionnelle et rollback en cas d'échec ; vérifier l'interaction des transactions imbriquées et des deux autorités. La réutilisation de B est empêchée par le registre permanent des occurrences ; si ce contrat change, la lecture `findUserId` seule ne suffit plus. Fonctionne entre instances seulement avec la discipline de CAS de tous les writers de slot.

### L4 — Stream Binding

**Lieu et transaction.** `ExternalIdentityBindingStreamJdbcRepository.lock` (`SELECT ... FOR UPDATE`) dans `JpaExternalIdentityBindingAdapter.acquireWithInitializer` et `detach`, `MANDATORY`. Les callers comprennent Attach/Detach et `ExecuteRegistrationService`, ce dernier dans la transaction Execute de Consumption. Chaîne Acquire : bootstrap `INSERT stream(E,0) ON CONFLICT DO NOTHING` → lock E → lecture actif → décision conflit/acquire → éventuel initializer User + fait → réservation B → insert actif conditionnel → `advance(R,R+1)` → append fact `(E,R+1)` → outcome/claim du caller → commit. Detach : lecture stream → lock E → lecture actif exact B → delete exact B → advance R → append fact → commit.

**Invariant et race.** Pour E, au plus un actif ; chaque transition committée consomme exactement une révision suivante et possède un fait correspondant ; un B ne revient jamais sous une autre occurrence. Sans le lock seul : T1 et T2 lisent E libre/R=5 ; T1 réserve B1, insère actif et avance R6 ; T2 peut décider sur E libre/R5 et réserver B2 ; l'insert actif ou le CAS R perd et doit rollbacker **tous** ses effets. Avec les opérations actuelles, ce rollback peut sauver l'intégrité mais la décision négative (conflit ou stale Detach) peut aussi être prise sous un snapshot périmé. T1 lit E occupée par B1/R5 et retourne conflit ; T2 détache B1/R6 ; le conflit T1 n'est plus ordonné à l'instant de son commit si la décision doit représenter l'autorité au commit. Pour Detach/Attach, un B supprimé ne doit jamais effacer un B ultérieur : `DELETE WHERE E AND B` le protège, mais R/fait doivent rester couplés. La PK active, PK B, UNIQUE `(E,R)` et le CAS `advance` arbitrent déjà des parties de l'invariant, sans imposer ensemble l'ordre de **toutes** les décisions.

**Classe P2.** Le lock est justifié **dans la représentation et le protocole actuels**. Une alternative serait un CAS **premier** sur `stream(E,current_revision)` de R vers R+1 pour toute transition positive, suivi sous ce même verrou SQL des lectures et écritures actif/B/fait dans une transaction. Un conflit ou `NOT_CURRENT` doit lui aussi être validé par une opération conditionnelle sur R avant d'être publié, ou être recalculé après un conflit technique ; le loser rollbacke et retente dans une nouvelle transaction. R est le token de fencing, B l'identité non réassignable, et `fenceExact(E,U,B,R)` de Command reste obligatoire. Crash avant commit rollbacke R/actif/B/fait/User/outcome ; plusieurs instances convergent via la même ligne E. **Obligation de preuve non satisfaite** : tous les writers, y compris Registration, doivent être coupés ensemble ; vérifier avec barrières PostgreSQL les décisions négatives, le bootstrap, l'ordre avec Command et le traitement des erreurs/retries. Le test `BindingOptimisticCasSemanticsPostgresTest` démontre qu'un `UPDATE stream SET R=R WHERE R=:old AND NOT EXISTS(active)` peut retourner 1 après avoir attendu une autre transaction qui a inséré l'actif **sans changer R**. On ne peut donc pas simplement ajouter ce prédicat et retirer `FOR UPDATE`.

## E. Audit du fencing, séparé du verrouillage

**Trois propriétés distinctes.** L'exclusion mutuelle détermine qui entre maintenant dans une section critique (`FOR UPDATE` du slot ou du stream). Le contrôle optimiste vérifie à la mutation que la version ou l'état lu fait toujours autorité (`UPDATE ... WHERE revision/claimId`). Le fencing empêche un ancien détenteur d'autorité de produire un effet après remplacement (`claimId` au terminal, ou `E,U,B,R` au commit Command). Un CAS peut prendre un verrou de ligne SQL implicite jusqu'au commit ; il n'est pas pour autant un `SELECT FOR UPDATE` préalable. Une PK évite un double insert mais ne fence pas, à elle seule, un acteur ancien sur une autre table.

| Situation A retardé, B avance | Check effectif au point critique | Conclusion |
|---|---|---|
| Claim C1 expire, C2 prend le slot | `terminalize`/`scheduleRetry` filtrent `current_claim_id=C1`; `ExecuteConsumptionService` lève `LostClaimException` dans la transaction ; `FinalizeConsumptionService` verrouille avant effet | C1 ne committe pas un effet SQL transactionnel après takeover. L'expiration seule ne retire pas C1 : le takeover committé le fait. Confiance élevée pour SQL inspecté. |
| Command observe E/B/R, Detach fait R+1 | `fenceExact` vérifie E/U/B/R par `UPDATE` du stream avant outcome/terminal claim ; l'échec rollbacke Pot/Event préparés | Ancienne Command fenced. Un fence gagnant tient le verrou SQL du stream au commit, donc Detach attend. Confiance élevée pour le chemin courant. |
| Command perd le fence | rollback, nouvelle transaction, slot courant verrouillé, contrôle B exact, rejet éventuel | Rejet par claim courant seulement ; le cas `B encore courant` devient conflit technique. Confiance moyenne : composition runtime non revalidée par la slice échouée. |
| Fact Binding ancien après fact récent | `CURRENT_BINDING` upsert seulement si R augmente ; à R égale payload comparé | Pas de régression ; pas une autorité WRITE. Confiance élevée statique. |
| Event LKV ancien après plus récent | upsert seulement si version augmente | Pas de régression. Confiance élevée statique. |
| Deux workers pour même ProjectionTask / résultat | slot par clé et claim, puis root/result PK/UNIQUE ; transaction finale | Écriture tardive SQL arrêtée par claim ou conflit d'unicité. Confiance moyenne hors tests runtime complets. |

**Fenêtres à surveiller.** Un `claimId` qui ne sert qu'à acquérir ne suffit pas : la mutation finale doit toujours le tester ou verrouiller le slot avant effet. `@Version` sur `JpaConsumptionSlotEntity.revision` n'est pas une preuve pour les requêtes SQL `UPDATE` directes ; leurs prédicats `current_claim_id` sont la preuve effective. Le fence Binding ne peut pas être remplacé par une simple lecture initiale. Une écriture vers une ressource hors de la transaction du slot ou du stream nécessiterait un token vérifié par cette ressource, ou une publication transactionnelle suivie d'un consumer idempotent. Aucun tel effet non transactionnel n'a été établi dans les chemins examinés.

## F. Binding : autorités et limites d'une alternative

L'autorité courante est **composite mais localisée par E** : stream permanent avec R, ligne active facultative `(E,U,B)`, registre permanent des B et fait append-only `(E,R)`. `CURRENT_BINDING` est un read model asynchrone, jamais l'arbitre d'Attach, Detach, Registration ou Command. Un Acquire gagnant modifie au minimum stream, actif, occurrence et fait ; Registration ajoute User, UserCreatedFact et outcome ; le terminal du claim appartient au même commit du worker. Detach modifie stream, actif et fait. La transaction atomique multi-table est indispensable ; elle n'implique pas automatiquement plusieurs autorités indépendantes.

Le seul `SELECT FOR UPDATE` explicite du writer Binding porte sur stream E. L'ordre documenté `stream → actif` est utile parce que le code actuel verrouille E avant de toucher la ligne active ; il ne démontre pas une nécessité intrinsèque de deux locks d'autorité. Les inserts/deletes/updates prennent aussi des locks SQL implicites. Une variante CAS-first conserverait un ordre déterministe E puis actif/fait, et doit être testée face au fence Command qui met à jour ce même stream après ses mutations Pot. Une variante « CAS actif puis CAS R » n'est pas suffisante : T1 pourrait gagner l'actif et T2 gagner R ou un crash pourrait laisser une moitié si les opérations ne partagent pas le même commit. De même, `UNIQUE(E)` seul prouve « au plus un actif », pas la continuité R, l'existence du fait ou l'ordre des décisions négatives.

La révision R doit augmenter pour **chaque** transition autoritative positive et ne jamais revenir à une ancienne valeur ; sinon un Command observant B/R peut franchir un fence ABA. B n'est pas réassigné grâce au registre d'occurrences. Le fence Command doit rester sur `E,U,B,R` au point tardif et dans la transaction des effets, même si le `SELECT FOR UPDATE` Binding disparaît un jour. La preuve WA historique du lock actuel reste valable ; l'audit ne la remplace pas par une hypothèse optimiste non testée.

## G. Opportunités et obligations de preuve

| Décision | Garantie actuelle → mécanisme proposé → obligation de preuve |
|---|---|
| SAFE / LOCAL, expérimentation L1 | Slot locké avant choix → CAS slot `revision/current_claim_id` puis écriture claim transactionnelle → deux workers, takeover/lease, rollback, retry, restart et plusieurs instances ; garder le lock tant que ces tests ne passent pas. |
| SAFE / LOCAL, expérimentation L2/L3 | Claim locké avant effet/rejet → CAS slot avant effet, terminal CAS et même transaction → race takeover/finalize dans les deux ordres, perte tardive du CAS, aucune fuite d'effet, propagation transactionnelle des ports. |
| ARCHITECTURAL, L4 | Stream E locké, actif/R/fait atomiques → protocole CAS-first commun à Attach/Detach/Registration + fence négatif prouvé → tests PostgreSQL à barrières incluant le contre-exemple `NOT EXISTS`, Command/Binding, bootstrap, décisions négatives, erreur SQL, crash/retry et cutover de tous les writers. |
| KEEP, pour l'instant | `fenceExact(E,U,B,R)` Command et checks `claimId` terminaux → les conserver ; ils expriment l'autorité au commit et ne sont pas des optimisations de lock. |
| UNKNOWN | Effets futurs hors SQL local, transaction manager/datasource des déploiements, runtime BINDING dont cinq tests ne démarrent pas → preuve ciblée avant toute conclusion de suppression. |

**Faux optimisme à éviter.** Deux CAS successifs sur des autorités réellement indépendantes ne donnent pas une mutation atomique commune. Lire l'actif puis insérer sans PK/UNIQUE est un check-then-act. Tester uniquement `lease_until` n'empêche pas un ancien worker de committer après takeover. Un `ON CONFLICT DO NOTHING` sans comparer le payload masque une divergence (les Result stores comparent le contenu après l'insert). Une révision réutilisée recrée ABA. Un loser SQL ne doit pas publier `Rejected` dans la transaction qui vient de perdre : rollback, nouveau snapshot, nouvelle décision. PostgreSQL `READ COMMITTED` ne réévalue pas nécessairement une sous-requête `EXISTS/NOT EXISTS` après attente sur la ligne cible, comme le test de caractérisation le démontre.

## Avis architectural

Le modèle `read authority → pure decision → conditional mutation/append → commit`, avec concurrence optimiste et fencing explicite, est **plausible** pour Pocoma. Pot, `CURRENT_BINDING`, LKV, résultats immuables, tâches et publications appliquent déjà des variantes de ce schéma. Les locks pessimistes restants expriment surtout la façon actuelle de sérialiser des autorités **locales** (slot ou E), plutôt qu'une propriété intrinsèque multi-autorité du domaine. Binding reste le cas difficile : l'autorité E est répartie entre stream, actif, occurrence et fait, et une tentative optimiste naïve a déjà échoué sur un comportement PostgreSQL observé. Le lock Binding actuel est donc la meilleure représentation **prouvée aujourd'hui** ; son remplacement est une hypothèse architecturale avec obligation de preuve, pas une correction mécanique. Aucun cas P1 n'a été démontré, mais cela ne prouve pas qu'il ne puisse pas en apparaître avec un effet externe ou un invariant futur.
