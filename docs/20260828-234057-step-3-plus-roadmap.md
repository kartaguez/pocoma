# Roadmap détaillée — Étapes 3 à 7

## Résumé

```text
Étape 3 — Nouveaux workers pull
Étape 4 — Persistence PostgreSQL cible
Étape 5 — Wiring, API durable et bascule progressive
Étape 6 — Retrait du legacy
Étape 7 — Validation opérationnelle et clôture
```

Décisions retenues :

- les endpoints synchrones actuels restent disponibles ;
- une API asynchrone durable séparée sera ajoutée ;
- la bascule sera progressive, pipeline par pipeline ;
- les nouveaux workers seront désactivés par défaut ;
- une Command sera idempotente grâce à un journal indexé par `commandId` ;
- une Task sera idempotente grâce à un journal indexé par `taskId` ;
- un `ExecutionGuard<K>` technique commun portera ces deux journaux sans dépendre de la consommation ;
- l'API async exigera une `Idempotency-Key` unique par utilisateur afin qu'un retry HTTP ne crée
  pas une seconde Command ;
- un worker traite strictement un seul élément, sans préfetch ni file locale ;
- pas de heartbeat ni retry automatique dans la première version ;
- sans heartbeat, `leaseDuration` devra être au moins trois fois supérieure à
  `maxNormalProcessingDuration` ;
- `FAILED` reste terminal ;
- le polling suffit à la correction, les notifications sont une optimisation ;
- la segmentation reste statique, sans coordinateur de grappe.

Invariant transversal : `ConsumptionSlot` est la source de vérité du lifecycle de processing.
Les statuts Command et Task sont des matérialisations réconciliables. La transition autoritative
précède toujours la matérialisation ; les processing engines réparent opportunément un durable
READY/PENDING associé à un slot terminal avant de retourner le prochain travail aux workers.

## Étape 3 — Nouveaux workers pull

### 3.1 — Boucle pull minimale

Ajouter dans l'orchestrateur une boucle séquentielle réutilisable qui gère start, stop, polling,
réveil optionnel et répétition immédiate après succès. Elle ne connaît aucun type de travail,
claim, lease, pipeline ou transaction et ne réutilise ni batch, queue ni pool legacy.

### 3.2 — `supra-worker-command`

Flux :

```text
ClaimNextCommandUseCase
→ CommandExecutionGuard(commandId)
→ ExecuteCommandUseCase
→ CompleteCommandProcessingUseCase
```

Une exception métier/applicative appelle fail ; un abandon avant traitement appelle release. Une
commande déjà journalisée n'est pas réexécutée et peut être complétée. Les commandes avec Pot sont
segmentées par `potId`; celles sans Pot restent visibles par tous les segments.

Le contrat générique `ExecutionGuard<K>` réside dans `engine-execution-guard`, hors de
`engine-consumption`. Son journal et l'effet métier partagent une transaction. Une erreur technique
dont l'issue de commit est inconnue ne transforme pas la Command en failure terminale : le claim
expire et le prochain propriétaire consulte le journal.

### 3.3 — `supra-worker-event`

Une instance logique est liée à un `PipelineDefinition` et un `WorkerSegment` :

```text
ClaimNextEventUseCase
→ CreateTasksForEventUseCase
→ CompleteEventProcessingUseCase
```

Zéro tâche est un succès. Les pipelines et versions consomment indépendamment le même Event.

### 3.4 — `supra-worker-task`

Flux :

```text
ClaimNextTaskUseCase
→ ExecutionGuard<UUID taskId>
     └── RecordedTaskExecutionMapper
         → ExecuteTaskUseCase
→ CompleteTaskProcessingUseCase
```

Le mapping durable vers typé est exécuté dans le callback du guard et résolu par
`pipelineId + pipelineVersion + taskType`. Ainsi `ALREADY_EXECUTED` ne sollicite ni codec ni
handler. Jackson ne pénètre ni dans le worker générique ni dans l'engine typé.
Une Task déjà journalisée n'est pas réexécutée et est complétée avec le claim courant. Un effet
externe devra utiliser une outbox transactionnelle ou `taskId` comme clé d'idempotence aval ; la
cible ne suppose pas que tous les handlers soient naturellement idempotents.

Les erreurs explicitement définitives de payload ou d'exécution deviennent `FAILED`. Mapper ou
handler absent, incohérence de wiring, panne technique ou issue de commit inconnue laissent le
claim expirer sans terminaliser la Task. Les slots terminaux et leurs failures historiques sont
réconciliés par `ClaimNextTaskUseCase` avant toute exposition au worker.

### 3.5 — Pipeline Balance

Extraire le décodage JSON dans `ComputeBalancesRecordedTaskMapper`, partagé temporairement par le
pont legacy et le nouveau TaskWorker. Ancien et nouveau workers ne seront pas actifs simultanément
pour le binding Balance.

### 3.6 — Tests

Prouver une seule unité par itération, le parallélisme par instances, complete/fail/release, la
multi-consommation Event, le routage Task exact, l'idempotence Command et l'absence de métier dans
les workers.

## Étape 4 — Persistence PostgreSQL cible

### 4.1 — Schéma générique

Créer `consumption_slots(namespace, components_json, revision, status)` et
`consumption_claims` avec claim id, token, worker, lease, dates de fin/invalidation et failure.
Le slot ne stocke pas de `currentClaimId`.
Ajouter un index unique partiel sur `(namespace, components_json)` lorsque `ended_at` et
`invalidated_at` sont nuls. Un claim expiré reste structurellement ouvert jusqu'à ce que la
transaction de reclaim l'invalide avant d'insérer son remplaçant. Cette contrainte complète le CAS
de révision du slot.

### 4.2 — `JpaClaimPort`

Garantir dans une transaction : création paresseuse, CAS de révision, invalidation de l'ancien
claim expiré, insertion du nouveau claim et incrément du slot. Completion/failure/release vérifient
clé, token et lease avant toute mutation.

Le port fournit aussi la failure immutable du claim ayant rendu un slot `FAILED`. Une failure
manquante pour un slot `FAILED` est une corruption technique, jamais une failure synthétique.

### 4.3 — Commands durables

Créer `commands` et `command_executions`. La Command persiste type/payload JSON, acteur/scopes,
`potId` optionnel, statut, failure et dates. Ajouter `SubmitCommandUseCase`; la soumission ne crée
aucun slot. L'ordre SQL est `createdAt, commandId`.

Chaque endpoint async exige `Idempotency-Key`. La clé est unique par utilisateur sur toute l'API
async et persiste avec un fingerprint canonique de l'intention. Un retry identique restitue le
`commandId` original ; une réutilisation avec un autre payload retourne `409 Conflict`.

### 4.4 — Journal Command

Le `ExecutionGuard<UUID>` Command ouvre une transaction, insère `command_executions`, exécute le
métier puis commit. Métier, outbox et journal committent ou rollback ensemble. Le même contrat est
instancié pour Task avec `task_executions`; projection/outbox et journal Task partagent la
transaction. Les deux adapters et journaux restent distincts.

### 4.5 — Events

Réutiliser `business_event_outbox` comme source de `RecordedEvent`. La sélection ignore le statut
global legacy, filtre `pipelineId + potId`, ordonne par version/date/id et s'appuie sur la
consommation `event/pipelineId/pipelineVersion/eventId`.

### 4.6 — Tasks

Réutiliser progressivement `tasks_4_pipeline`, ajouter `target_version`, préserver les colonnes
legacy durant la transition et implémenter `TaskPort`. Task creation persiste atomiquement
l'idempotence et zéro à N tâches.

### 4.7 — Transactions

Le slot, le claim courant, son historique et le fencing forment la transaction autoritative du
`ClaimPort`. Pour complete/fail Command et Task, cette transaction commit d'abord ; le statut du
durable est ensuite matérialisé best effort. Un échec de matérialisation laisse donc un slot
terminal et une ligne READY/PENDING, réparée au prochain polling. Il n'existe plus de transaction
commune slot terminal + statut Command/Task. Event ne modifie jamais sa source.

### 4.8 — Tests PostgreSQL

Avec Testcontainers : CAS réel, slot absent concurrent, index unique partiel, reclaim d'un claim
expiré, fencing, rollback, ordre, segmentation, multi-consommation Event, journaux Command/Task,
soumissions async concurrentes et compatibilité historique.

## Étape 5 — Wiring, API durable et bascule progressive

### 5.1 — Wiring

Assembler les use cases génériques complete/fail transactionnels dans les services spécialisés
Command/Task non redécorés extérieurement. Le `CommandPort`/`TaskPort` de matérialisation est appelé
après le commit du lifecycle. Claim/release et Event conservent leurs frontières prévues.

### 5.2 — Configuration

Préfixes `pocoma.command-processing`, `pocoma.event-processing` et `pocoma.task-processing`.
Paramètres : enabled=false, worker id, lease, durée normale maximale, polling, segment index/count ;
Event/Task ajoutent leurs bindings pipeline. Le démarrage refuse
`leaseDuration < 3 × maxNormalProcessingDuration`. Aucun batch, pool, queue, heartbeat ou retry.

### 5.3 — Runtimes

Créer `runtime-command-worker`, `runtime-event-worker`, `runtime-task-worker`. Le parallélisme
horizontal vient de plusieurs processus ; chaque worker reste séquentiel.

### 5.4 — API asynchrone

Conserver `/api/pots` et `/api/expenses`. Ajouter `/api/async/pots...`, avec `potId` explicite dans
les routes Expense et header `Idempotency-Key` obligatoire. Une première soumission ou un retry
identique répond 202 `{commandId,status,createdAt}` avec le même identifiant et Location
`/api/commands/{id}`. Une même clé réutilisée par le même utilisateur avec une autre requête répond
409. Le GET de suivi n'exécute aucun métier.

### 5.5 à 5.7 — Bascule

Déployer les nouveaux workers désactivés. Pour chaque pipeline, arrêter le worker legacy, attendre
ses claims, activer le nouveau worker puis comparer les compteurs. Activer ensuite CommandWorker
et l'API async tout en conservant la voie synchrone.

### 5.8 — Observabilité

Compter claims tentés/gagnés, complete/fail/release, ownership lost, idle, guards exécutés/déjà
exécutés, soumissions créées/rejouées/en conflit, durées et ratio durée/lease. Observer à 80 % de la
lease et signaler tout dépassement. Les labels
restent bornés : worker, pipeline, version, segment, outcome ; aucun identifiant métier.
Ajouter les réconciliations completed/failed, échecs de matérialisation et retards de convergence.

## Étape 6 — Retrait du legacy

Après migration de tous les bindings :

1. supprimer task materialization, son supra, son runtime et ses adapters ;
2. supprimer l'exécution Task legacy, `LegacyPipelineTask`, bindings et pont JSON ;
3. supprimer les use cases/workers de projection legacy et leurs types `engine.model` ;
4. supprimer `BusinessEventEnvelope`, `PotPartitioner`, `ProjectionPartition` et `engine.legacy` ;
5. nettoyer Maven, Spring, propriétés et l'allow-list infra vers supra.

Les tables/colonnes historiques restent d'abord en lecture seule. Leur suppression physique fera
l'objet d'une migration séparée après sauvegarde et période de rétention.
Leurs statuts restent des projections du slot ; une réconciliation est exécutée avant toute
suppression de colonne ou d'adapter historique.

## Étape 7 — Validation opérationnelle

Tester bout en bout API async idempotente → Command → Event → Task → Balance → Query, les crashes
avant effet, pendant transaction et après commit avant complete, les expirations, reclaims, tokens
obsolètes et failures terminales. Prouver qu'un effet Command/Task commité n'est pas répété et que
la création de Tasks reste idempotente par pipeline/version/Event. Lancer plusieurs instances par
niveau et segment, puis des tests de charge/backpressure. Documenter le dimensionnement des leases,
les limites de la V1 sans heartbeat, l'architecture, les workers, claims, guards et métriques.
Injecter aussi un échec de matérialisation après commit d'un slot Command/Task terminal, puis
vérifier sa réparation au passage suivant sans invocation du métier, du handler ou du guard.

La refonte est close lorsque les trois nouveaux workers sont les seuls workers pull, que les voies
sync/async partagent les use cases métier, que les claims PostgreSQL sont atomiques et fenced, que
le legacy est retiré et que le build, les tests multi-instance et ArchUnit passent.

## Hypothèses

- `FAILED` reste terminal ; `release` concerne l'abandon avant traitement.
- `ExecutionGuard` et claim répondent à deux problèmes distincts et ne dépendent pas l'un de l'autre.
- Une Task externe utilise une outbox ou une idempotence aval fondée sur `taskId`.
- `Idempotency-Key` est obligatoire et unique par utilisateur ; elle vit aussi longtemps que la Command en V1.
- Un claim ouvert est défini par `ended_at IS NULL AND invalidated_at IS NULL`.
- La V1 valide `leaseDuration >= 3 × maxNormalProcessingDuration`; heartbeat reste hors scope.
- Aucun verrou global par Pot ; les conflits restent optimistes.
- NATS/Spring ne sont jamais requis pour la correction du pull.
- La segmentation est statique.
- Le premier pipeline migré est `balance-projection`, version 1.
- Toute suppression de données historiques demande une décision de rétention séparée.
