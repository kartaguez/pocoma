# Roadmap détaillée — Étapes 3 à 7

## Résumé

```text
Étape 3 — Nouveaux workers pull
Étape 4 — Persistence PostgreSQL cible
Étape 5 — Wiring, API durable et bascule progressive
Étape 6 — Retrait du legacy
Étape 7 — Validation opérationnelle et clôture
```

Décisions retenues :

- les endpoints synchrones actuels restent disponibles ;
- une API asynchrone durable séparée sera ajoutée ;
- la bascule sera progressive, pipeline par pipeline ;
- les nouveaux workers seront désactivés par défaut ;
- une Command sera idempotente grâce à un journal indexé par `commandId` ;
- un worker traite strictement un seul élément, sans préfetch ni file locale ;
- pas de heartbeat ni retry automatique dans la première version ;
- `FAILED` reste terminal ;
- le polling suffit à la correction, les notifications sont une optimisation ;
- la segmentation reste statique, sans coordinateur de grappe.

## Étape 3 — Nouveaux workers pull

### 3.1 — Boucle pull minimale

Ajouter dans l'orchestrateur une boucle séquentielle réutilisable qui gère start, stop, polling,
réveil optionnel et répétition immédiate après succès. Elle ne connaît aucun type de travail,
claim, lease, pipeline ou transaction et ne réutilise ni batch, queue ni pool legacy.

### 3.2 — `supra-worker-command`

Flux :

```text
ClaimNextCommandUseCase
→ CommandExecutionGuard(commandId)
→ ExecuteCommandUseCase
→ CompleteCommandProcessingUseCase
```

Une exception métier/applicative appelle fail ; un abandon avant traitement appelle release. Une
commande déjà journalisée n'est pas réexécutée et peut être complétée. Les commandes avec Pot sont
segmentées par `potId`; celles sans Pot restent visibles par tous les segments.

### 3.3 — `supra-worker-event`

Une instance logique est liée à un `PipelineDefinition` et un `WorkerSegment` :

```text
ClaimNextEventUseCase
→ CreateTasksForEventUseCase
→ CompleteEventProcessingUseCase
```

Zéro tâche est un succès. Les pipelines et versions consomment indépendamment le même Event.

### 3.4 — `supra-worker-task`

Flux :

```text
ClaimNextTaskUseCase
→ RecordedTaskExecutionMapper
→ ExecuteTaskUseCase
→ CompleteTaskProcessingUseCase
```

Le mapping durable vers typé reste dans l'adaptateur entrant et est résolu par
`pipelineId + pipelineVersion + taskType`. Jackson ne pénètre pas dans l'engine typé.

### 3.5 — Pipeline Balance

Extraire le décodage JSON dans `ComputeBalancesRecordedTaskMapper`, partagé temporairement par le
pont legacy et le nouveau TaskWorker. Ancien et nouveau workers ne seront pas actifs simultanément
pour le binding Balance.

### 3.6 — Tests

Prouver une seule unité par itération, le parallélisme par instances, complete/fail/release, la
multi-consommation Event, le routage Task exact, l'idempotence Command et l'absence de métier dans
les workers.

## Étape 4 — Persistence PostgreSQL cible

### 4.1 — Schéma générique

Créer `consumption_slots(namespace, components_json, revision, status)` et
`consumption_claims` avec claim id, token, worker, lease, dates de fin/invalidation et failure.
Le slot ne stocke pas de `currentClaimId`.

### 4.2 — `JpaClaimPort`

Garantir dans une transaction : création paresseuse, CAS de révision, invalidation de l'ancien
claim expiré, insertion du nouveau claim et incrément du slot. Completion/failure/release vérifient
clé, token et lease avant toute mutation.

### 4.3 — Commands durables

Créer `commands` et `command_executions`. La Command persiste type/payload JSON, acteur/scopes,
`potId` optionnel, statut, failure et dates. Ajouter `SubmitCommandUseCase`; la soumission ne crée
aucun slot. L'ordre SQL est `createdAt, commandId`.

### 4.4 — Journal Command

`CommandExecutionGuard` ouvre une transaction, détecte une exécution existante ou exécute le
métier puis journalise `commandId`. Métier, outbox et journal committent ou rollback ensemble.

### 4.5 — Events

Réutiliser `business_event_outbox` comme source de `RecordedEvent`. La sélection ignore le statut
global legacy, filtre `pipelineId + potId`, ordonne par version/date/id et s'appuie sur la
consommation `event/pipelineId/pipelineVersion/eventId`.

### 4.6 — Tasks

Réutiliser progressivement `tasks_4_pipeline`, ajouter `target_version`, préserver les colonnes
legacy durant la transition et implémenter `TaskPort`. Task creation persiste atomiquement
l'idempotence et zéro à N tâches.

### 4.7 — Transactions

Les décorateurs spécialisés englobent le service générique non décoré. Claim Command et Task
couvrent source + slot + historique ; Event ne modifie jamais sa source.

### 4.8 — Tests PostgreSQL

Avec Testcontainers : CAS réel, slot absent concurrent, reclaim, fencing, rollback, ordre,
segmentation, multi-consommation Event, journal Command et compatibilité historique.

## Étape 5 — Wiring, API durable et bascule progressive

### 5.1 — Wiring

Assembler ports JPA, services génériques non décorés et décorateurs externes spécialisés, sans
transactions imbriquées indépendantes.

### 5.2 — Configuration

Préfixes `pocoma.command-processing`, `pocoma.event-processing` et `pocoma.task-processing`.
Paramètres : enabled=false, worker id, lease, polling, segment index/count ; Event/Task ajoutent
leurs bindings pipeline. Aucun batch, pool, queue, heartbeat ou retry.

### 5.3 — Runtimes

Créer `runtime-command-worker`, `runtime-event-worker`, `runtime-task-worker`. Le parallélisme
horizontal vient de plusieurs processus ; chaque worker reste séquentiel.

### 5.4 — API asynchrone

Conserver `/api/pots` et `/api/expenses`. Ajouter `/api/async/pots...`, avec `potId` explicite dans
les routes Expense, réponse 202 `{commandId,status,createdAt}`, Location `/api/commands/{id}` et un
GET de suivi sans exécution métier.

### 5.5 à 5.7 — Bascule

Déployer les nouveaux workers désactivés. Pour chaque pipeline, arrêter le worker legacy, attendre
ses claims, activer le nouveau worker puis comparer les compteurs. Activer ensuite CommandWorker
et l'API async tout en conservant la voie synchrone.

### 5.8 — Observabilité

Compter claims tentés/gagnés, complete/fail/release, ownership lost, idle et durées. Les labels
restent bornés : worker, pipeline, version, segment, outcome ; aucun identifiant métier.

## Étape 6 — Retrait du legacy

Après migration de tous les bindings :

1. supprimer task materialization, son supra, son runtime et ses adapters ;
2. supprimer l'exécution Task legacy, `LegacyPipelineTask`, bindings et pont JSON ;
3. supprimer les use cases/workers de projection legacy et leurs types `engine.model` ;
4. supprimer `BusinessEventEnvelope`, `PotPartitioner`, `ProjectionPartition` et `engine.legacy` ;
5. nettoyer Maven, Spring, propriétés et l'allow-list infra vers supra.

Les tables/colonnes historiques restent d'abord en lecture seule. Leur suppression physique fera
l'objet d'une migration séparée après sauvegarde et période de rétention.

## Étape 7 — Validation opérationnelle

Tester bout en bout API async → Command → Event → Task → Balance → Query, les crashes à chaque
frontière, les tokens obsolètes et les failures terminales. Lancer plusieurs instances par niveau
et segment, puis des tests de charge/backpressure. Documenter architecture, workers, récupération,
claims, segmentation et métriques.

La refonte est close lorsque les trois nouveaux workers sont les seuls workers pull, que les voies
sync/async partagent les use cases métier, que les claims PostgreSQL sont atomiques et fenced, que
le legacy est retiré et que le build, les tests multi-instance et ArchUnit passent.

## Hypothèses

- `FAILED` reste terminal ; `release` concerne l'abandon avant traitement.
- Aucun verrou global par Pot ; les conflits restent optimistes.
- NATS/Spring ne sont jamais requis pour la correction du pull.
- La segmentation est statique.
- Le premier pipeline migré est `balance-projection`, version 1.
- Toute suppression de données historiques demande une décision de rétention séparée.
